# 一、商家主页 Redis 缓存（Cache Aside + 防三缓）

## Cache Aside 是什么？读写流程是什么？

Cache Aside（旁路缓存）是最常用的缓存模式，应用层手动管理缓存，数据库是唯一权威数据源。

**读流程：**
```
① 先查缓存
   ├── 命中（hit）→ 直接返回，不查 DB
   └── 未命中（miss）→ 查 DB → 将结果写入缓存（设 TTL）→ 返回
```

**写流程：**
```
① 更新数据库
② 删除缓存（不是写入新值）
```

**四种缓存写策略横向对比：**

| 策略 | 写操作 | 优点 | 缺点 |
|------|--------|------|------|
| **Cache Aside** | 写 DB → 删缓存 | 只缓存真正被读的数据 | 有短暂不一致窗口 |
| **Write Through** | 同步写缓存 + 写 DB | 写后立即一致 | 写延迟高，不热数据也占内存 |
| **Write Back** | 只写缓存，异步刷盘 | 写性能最高 | 断电丢数据，实现复杂 |
| **Write Around** | 只写 DB，绕过缓存 | 避免热点污染 | 写后首次读必然 miss |

## Q1：商家主页为什么要加缓存？直接查数据库有什么问题？

> 代码位置：`MerchantServiceImpl.getDetail()`

商家主页是高频读、低频写的场景。每次直接查 MySQL 有两个代价：DB IO 延迟（几十毫秒），高并发下打满连接池影响其他业务。加 Redis 缓存后命中时降到个位数毫秒。

**↳ 追问：Redis 是单线程的，为什么还能支撑高并发？**

Redis 的"单线程"指命令处理线程只有一个，但这正是它高性能的来源：单线程避免了锁竞争和上下文切换开销。网络 IO 层用 epoll/kqueue 实现 IO 多路复用，一个线程同时监听成千上万个连接，只在有数据可读时才处理。加之 Redis 所有操作都在内存完成，没有磁盘 IO，单线程每秒可处理 10 万以上命令。

---

## Q2：getDetail() 里同时防了穿透、击穿、雪崩三个问题，分别是什么场景，各自怎么解决的？

> 代码位置：`MerchantServiceImpl.getDetail()`

**穿透**：key 在 Redis 和 DB 都不存在，解法：写空值哨兵（TTL 2 分钟）。

**击穿**：热门 key 刚过期，瞬间大量请求穿透到 DB，解法：Redisson 分布式锁 + 锁内 DCL。

**雪崩**：大量 key 同时过期，解法：TTL 随机偏移 25~35 分钟。

**↳ 追问：空值哨兵的 TTL 为什么设 2 分钟，而不是和正常缓存一样的 30 分钟？**

空值哨兵代表"当前这个 id 不存在"，但这个结论会过时：商家注册后 id 就从"不存在"变成"存在"了。如果 TTL 设 30 分钟，新注册的商家要等 30 分钟才能被搜到，业务上不可接受。2 分钟是"防穿透效果"与"新数据可见延迟"的平衡点——2 分钟内的穿透攻击被挡住，正常用户最多等 2 分钟看到新商家。

## Q3：防缓存击穿时，为什么还需要在锁内再查一次缓存？（DCL 是怎么回事）

> 代码位置：`MerchantServiceImpl.getDetail()`

```java
// 第一次查缓存（锁外，并发执行）
String cached = stringRedisTemplate.opsForValue().get(cacheKey);
if (cached != null) { return ...; }

// 加锁
lock.lock();

// 第二次查缓存（锁内，串行执行）
cached = stringRedisTemplate.opsForValue().get(cacheKey);
if (cached != null) { return ...; }  // 前一个线程已重建好，直接用

// 真正查 DB
```

| | 第一次（锁外） | 第二次（锁内） |
|---|---|---|
| 目的 | 正常命中时快速返回，不排队抢锁 | 复用前一个线程重建好的缓存 |
| 有无锁保护 | 无 | 有 |

**↳ 追问：这个 DCL 和 Java 双重检查锁（DCL 单例）是同一个模式吗？原理上有什么共同点？**

本质相同，都是"在获取锁之前和之后各做一次条件检查"。Java DCL 单例中，锁外检查避免每次创建都抢锁，锁内检查避免多个线程都通过了锁外检查后重复初始化。这里的逻辑完全一致：锁外快速返回已缓存数据，锁内防止排队的线程都查 DB。Java DCL 还需要 `volatile` 来禁止指令重排，因为对象初始化不是原子的；而这里的 Redis set 和 get 各自是原子操作，不需要类似的内存屏障。

## Q4：商家信息更新后，为什么选"改 DB → 删缓存"，而不是"改 DB → 更新缓存"或"先删缓存 → 再改 DB"？

> 代码位置：`MerchantServiceImpl.updateInfo()`

**方案一（改 DB → 更新缓存）**：并发写时有覆盖问题，两次写 DB 和写缓存的顺序无法保证，可能导致旧值覆盖新值。

**方案二（先删缓存 → 再改 DB）**：删缓存后，其他线程读 miss 查到旧 DB 值并回填，之后 DB 才更新，造成旧值在缓存里长期存在。

**方案三（改 DB → 删缓存）**：删除幂等，最终状态是缓存不存在，下次从 DB 拿最新值。

**↳ 追问：方案三还是存在极小概率的不一致（Q5 提到的窗口），有没有能完全消除的方案？**

理论上可以用"延迟双删"缓解：改 DB 后立即删缓存，再等几百毫秒后第二次删缓存，把 Q5 里那个短窗口内回填的旧值也清掉。但"延迟"的时间难以准确估计，且仍有极小窗口。要做到强一致，只能引入分布式事务（如 Seata），保证 DB 写入和缓存删除要么都成功要么都回滚，代价是引入 2PC 的性能损耗和实现复杂度。对于商家详情这种场景，轻微延迟一致性完全可接受，强一致代价远超收益。

---

## Q5：Cache Aside 防三缓这套方案有没有缺点？能做到强一致性吗？

不能做到强一致性，存在短暂不一致窗口：

```
线程A：读缓存 miss → 查 DB 拿旧值
线程B：更新 DB → 删缓存
线程A：将旧值写入缓存  ← 缓存是旧值，DB 是新值
```

这个窗口极短（几毫秒），对商家详情场景完全可接受。

**↳ 追问：如果业务上真的需要强一致，比如金融场景，应该怎么处理？**

有三条路：① 直接不缓存，每次读 DB，牺牲性能换一致性；② 引入 Seata 分布式事务（AT 模式），框架层面保证 DB 和 Redis 操作在同一个全局事务里，代价是每次写操作增加多次网络交互；③ 用 DB 事务 + Outbox 模式，把"删缓存"这个动作记录进 DB，由独立 relay 服务保证"DB 写成功则缓存最终一定被删"。哪种方案取决于对性能和一致性的权重，金融场景通常选① 或 Seata。

# 二、Spring Security + JWT 认证与鉴权

## Q23：JWT 登录的完整流程是什么？token 存在哪里，后续请求怎么验证？

> 代码位置：`UserServiceImpl.buildLoginVO()` + `JwtAuthenticationFilter` + `SecurityConfig`

**登录时**：`JwtUtil.generate(userId)` 生成三段式 JWT（Header.Payload.Signature），Payload 自包含 userId 和 exp（7天过期），HS256 签名，不写 Redis，服务端零状态。前端存 localStorage。

**后续请求**：Axios 拦截器注入 Header `token` → `JwtAuthenticationFilter` 验签解析得 userId（纯计算，无 IO）→ 写入 SecurityContextHolder → Security 规则放行或 401。

**Service 层**：`SecurityUtil.getCurrentUserId()` 从 ThreadLocal 读 userId，O(1)。请求结束后 Spring Security 自动清 ThreadLocal。

| | Sa-Token（原方案） | Spring Security + JWT（现方案） |
|---|---|---|
| 服务端存储 | Redis（token → userId） | 无（完全无状态） |
| 验证方式 | 查 Redis（有 IO） | 验签解析（纯计算） |
| 主动失效 | 支持（删 Redis key） | 不支持 |

**↳ 追问：JWT 不存 Redis，那 token 在 7 天过期前，如果用户被封号或者修改了密码，怎么让 token 立刻失效？**

这是 JWT 无状态的固有代价。有两种常见方案：① Redis 黑名单：封号时把该 token 的 jti（JWT ID）写入 Redis，每次验签后额外查一次 Redis 黑名单，命中则拒绝。缺点是引入了 IO，丧失了"纯计算验证"的优势，且黑名单随时间积累会变大（需按 exp 定期清理）；② 缩短 token 有效期 + refresh token：access token 有效期设 15 分钟，配合有效期 7 天的 refresh token 静默续签。封号时拒绝 refresh token 续签，最多 15 分钟后 access token 自动失效。项目当前未实现，是已知缺陷。

## Q24：为什么 JWT token 放 Header 而不放 Cookie？两种方式的安全边界是什么？

Cookie 是浏览器自动携带的，有 CSRF 风险——攻击者诱导用户访问恶意页面，浏览器自动带上 Cookie，伪造合法请求。Header token 需要 JS 主动设置，CSRF 无法控制 JS（同源策略），天然防 CSRF。代价是 XSS 可以窃取 localStorage 里的 token。

**↳ 追问：HttpOnly Cookie 是怎么防 XSS 的？如果用了 HttpOnly Cookie，CSRF 怎么防？**

`HttpOnly` 标志让 Cookie 对 JavaScript 不可见，`document.cookie` 读不到它，XSS 脚本无法窃取。这是 Cookie 方案相对 localStorage 的安全优势。但 HttpOnly Cookie 仍然会被浏览器自动携带，所以 CSRF 问题依然存在，需要配合 CSRF Token（SameSite=Strict 或在请求里加一个 double-submit cookie）来防御。两种方案本质上是防 XSS 和防 CSRF 之间的取舍，没有同时完美防两者的方案，只能根据业务场景选优先级。

## Q25：项目密码原来用 MD5 存储，有什么安全缺陷？已经怎么修复的？

> 代码位置：`UserServiceImpl.register()` / `UserServiceImpl.login()`

MD5 是确定性函数，相同明文永远生成相同哈希，没有加盐，彩虹表可以直接反推。

改用 BCrypt：内置随机盐（盐存在哈希字符串里），相同密码每次 encode 结果不同，彩虹表完全失效。work factor 可调，算得越慢越抗暴力破解。

```java
// 注册
user.setPassword(passwordEncoder.encode(dto.getPassword()));
// 登录：matches() 自动从哈希里提取盐再比较
if (!passwordEncoder.matches(dto.getPassword(), user.getPassword())) { ... }
```

**↳ 追问：BCrypt 既然这么好，为什么业界还有人用 Argon2？BCrypt 有什么不足？**

BCrypt 设计于 1999 年，是 CPU 密集型算法，但现代 GPU 可以大规模并行破解 CPU 密集型哈希。Argon2（2015 年密码哈希竞赛冠军）是内存密集型算法，每次哈希需要消耗大量内存（可配置），GPU 并行破解的优势被内存带宽限制抵消，抗 GPU/ASIC 暴力破解能力更强。Spring Security 5.x 开始支持 Argon2。项目用 BCrypt 对当前规模完全够用，但如果是高安全要求的场景（如金融、医疗），Argon2 是更现代的选择。


## Q43：客人发起预约时，如何防止同一用户并发重复提交？

> 代码位置：`BookingServiceImpl.create()`

```java
String lockKey = "booking:create:" + userId + ":" + scheduleId;
RLock lock = redissonClient.getLock(lockKey);
boolean locked = lock.tryLock(3, 30, TimeUnit.SECONDS);
if (!locked) throw new BusinessException("操作频繁，请稍后再试");

try {
    // DCL：锁内再查一次
    Booking exist = bookingMapper.selectOne(...);
    if (exist != null) throw new BusinessException(ResultCode.BOOKING_DUPLICATE);
    // 创建预约
} finally {
    if (lock.isHeldByCurrentThread()) lock.unlock();
}
```

**lock key 同时包含 userId 和 scheduleId**：不同档期的预约完全独立，锁粒度最小化，最大化并发吞吐。

**↳ 追问：leaseTime 设 30 秒，如果业务只需要 200ms，这 30 秒会有什么隐患？Redisson 的看门狗机制是什么？**

leaseTime 是"锁持有上限"，防止 JVM 崩溃时锁永远不释放（死锁）。正常情况 200ms 执行完后 finally 块手动 unlock，30 秒的 leaseTime 不会有影响。如果不显式设 leaseTime（传 -1），Redisson 会启动"看门狗（Watchdog）"——默认每隔 10 秒自动续期一次（续到 30 秒），只要持锁线程还活着就一直续。JVM 崩溃后续期停止，Redis 的 key 等 30 秒自动过期释放锁。两种方式都能防死锁，显式 leaseTime 更简单，看门狗更适合执行时间不确定的长事务。

## Q44：预约状态机是怎么设计的？为什么 status=1（待付款）不使用？

```
0（待确认）──confirm()──▶ 2（已定档）──complete()──▶ 3（已完成）
     │                                                      │
     └─────────────────cancel()─────────────────────────▶ 4（已取消）
```

status=1 在数据库枚举中保留但不使用，是为后续接入支付时无需改 schema，直接插入 `0→1→2` 流转即可。

每次变更前校验前置状态，不合法则抛 `BOOKING_STATUS_ERROR`（ResultCode=20003）。

**↳ 追问：状态机校验在 Service 层做，如果两个线程并发调用 confirm() 会有问题吗？如何解决？**

会有竞态：两个线程都查到 status=0，都通过了校验，都执行 UPDATE，最终执行了两次状态变更（虽然结果一样都是 2）。更危险的是并发 cancel 和 confirm——一个设为 4，一个设为 2，最终状态取决于哪个 UPDATE 后执行，与业务预期不符。解法是让 UPDATE 语句携带前置状态条件：`UPDATE booking SET status=2 WHERE id=? AND status=0`，然后检查 affected rows。如果 affected rows=0，说明被并发改了，抛异常。这是 CAS（Compare-And-Set）思想在数据库层的应用，比加分布式锁更轻量。

## Q45：超时未确认的预约怎么自动取消？为什么用 XXL-Job 而不是本地 @Scheduled？

> 代码位置：`BookingJobHandler.java`，注册名 `cancelTimeoutBookingJob`

XXL-Job 执行流程：定时扫描 status=0 且 create_time 超过 48 小时的预约 → 批量 UPDATE status=4 → MQSender 发取消通知 → WebSocket 推给客人。

@Scheduled 在多实例部署下每个实例都会触发，导致重复取消。XXL-Job 是分布式调度平台，同一任务同一时刻只分配给一个执行器实例。

**↳ 追问：批量 UPDATE 几百条记录，会不会造成 MySQL 长时间锁等待影响其他业务？怎么优化？**

UPDATE WHERE 条件走索引（id 或复合索引）时，锁的是行锁不是表锁，但如果一次 UPDATE 几百条，这几百个行锁会同时持有到事务提交，期间其他事务读这些行需要等待。优化方案是分批执行：每次 UPDATE LIMIT 100，提交事务，释放行锁，再执行下一批。这样把一个大事务拆成多个小事务，单次持锁时间从"几百行"缩短到"100 行"，大幅降低对其他业务的影响。代价是整个扫描任务耗时增加，但定时任务对时延不敏感，完全可接受。

## Q46：档期月历是怎么查询的？

```sql
SELECT * FROM schedule
WHERE merchant_id = ?
  AND DATE_FORMAT(date, '%Y-%m') = ?
```

返回当月所有档期，前端渲染日历：无档期灰色不可点，有档期绿色可点击预约，已满标色不可点。

**↳ 追问：DATE_FORMAT 函数在 WHERE 条件里，会不会导致索引失效？怎么优化？**

会导致索引失效。`DATE_FORMAT(date, '%Y-%m')` 是函数调用，MySQL 无法用 `date` 列上的索引，需要全表扫描。优化方案：把函数移到右侧，用范围查询代替：`WHERE merchant_id = ? AND date >= '2026-09-01' AND date < '2026-10-01'`。这样 `(merchant_id, date)` 联合索引可以完整使用，先定位商家再按日期范围筛选，复杂度从全扫降到 O(log n)。

## Q47：问卷模板是怎么设计的？客人的填写答案存在哪里？

商家创建 `QuestionnaireTemplate`（题目 + 题型），绑定账号。客人预约时拉取模板渲染表单，答案以 JSON 随 `BookingCreateDTO` 提交，存入 `booking.questionnaire_answers` 列。

**↳ 追问：答案存 JSON 列，如果将来要按答案内容搜索（比如"找所有填了'北京'的预约"），怎么查？**

MySQL 5.7+ 可以用 JSON 函数：`WHERE JSON_EXTRACT(questionnaire_answers, '$.city') = '北京'`，但这是全表扫描，性能差。如果这种查询是高频需求，有两条路：① 把关键答案字段（如城市）提取成独立列，加普通索引；② 把数据同步到 Elasticsearch，用 term 查询。项目当前问卷答案只用于展示给商家，不做搜索，JSON 存储足够。如果将来有搜索需求，按需提取列是最低成本的方案。

# 四、抢档期排队（Lua + Redis ZSET）

## 抢档期为什么用 Redis 而不用 MySQL？有其他业界方案吗？

MySQL 做不好的原因：FOR UPDATE 锁竞争、连接池耗尽、磁盘 IO 慢、无原生排名操作。

| 方案 | 并发能力 | 实现复杂度 | 适用场景 |
|------|---------|-----------|---------|
| MySQL FOR UPDATE | 低 | 低 | 低并发 |
| **Redis Lua + 直写 MySQL** | 高 | 中 | **当前方案** |
| MQ 排队 | 极高 | 高 | 大流量秒杀 |
| Redis 预检 + MQ 落库 | 极高 | 高 | 生产级秒杀，当前方案升级版 |

---

## Q12：抢档期为什么要用 Lua 脚本？不能用 Redisson 锁或者 Redis 事务（MULTI/EXEC）吗？

假设队列还剩 1 个名额，两用户同时发请求：

```
用户A ZSCORE → nil   用户B ZSCORE → nil
用户A ZCARD  → 9     用户B ZCARD  → 9
用户A ZADD 成功      用户B ZADD 成功  ← 超额！
```

Lua 脚本在 Redis 单线程上原子执行，三步整体不可分割，从根本上消除竞态。

**分布式锁**：5 次网络往返，Java 线程等锁期间阻塞线程池，高并发下线程池耗尽。

**MULTI/EXEC + WATCH**：EXEC 前命令只是入队，无法读取中间结果做条件判断。WATCH 乐观锁高并发下重试风暴，越忙越慢。

**Lua 方案**：1 次网络往返，Java 线程不阻塞，吞吐高延迟稳定。

**↳ 追问：Lua 脚本在 Redis 里是"原子"的，这个原子和数据库事务的 ACID 原子性是同一个概念吗？**

不完全相同。Redis Lua 的"原子"仅指执行过程不可被其他命令插入（单线程串行保证），没有回滚语义——如果 Lua 脚本执行到一半出错（比如类型错误），已执行的命令不会撤销。数据库事务的原子性包含回滚：事务内任何步骤失败，所有已执行操作都会被撤回，保证"要么全做要么全不做"。此外，数据库事务的原子性是 ACID 的一部分，还配套有持久化（D）和隔离（I）；Redis Lua 没有这些保证。简单说：Redis Lua 原子 = 不可打断；DB 事务原子 = 不可打断 + 可回滚 + 持久化。

## Q13：排队数据为什么用 Redis ZSET 而不用 LIST？

| 操作 | LIST | ZSET |
|------|------|------|
| 去重（一人只能入队一次）| LPOS，O(n) | ZSCORE，O(log n) |
| 查询排名 | 遍历，O(n) | ZRANK，O(log n) |
| 先来先得顺序 | 插入顺序，无法防重复 | score=时间戳，天然有序 |

**↳ 追问：ZSET 内部是什么数据结构？为什么 ZRANK 是 O(log n) 而不是 O(1)？**

ZSET 内部有两种编码：元素少（默认 128 个以内）且 member 较短时用 listpack（紧凑型双向链表，节省内存）；元素多时用跳表（skiplist）+ 哈希表。哈希表用于 O(1) 的 ZSCORE（按 member 查 score），跳表用于 O(log n) 的有序操作（ZRANK/ZADD/ZRANGE）。ZRANK 无法做到 O(1) 是因为需要在有序结构里找到 member 的位置，跳表的多层索引让这个查找是 O(log n)，类似二分查找，无法更快。

## Q14：rush.lua 返回值为什么用 -1 / 0 / 正整数这种编码？

- `-1`：已入队（业务正常，不是系统错误）
- `0`：队列已满
- `>0`：排队名次（ZRANK 返回 0-based，脚本内 +1 转成 1-based）

Java 侧只需判断区间，选整数是因为 Redis execute 返回 `Long` 类型，不需要解析字符串。

**↳ 追问：Lua 函数能返回的类型有哪些限制？如果想返回一个包含名次和时间戳的复合对象，怎么做？**

Redis Lua 脚本的返回值只能是以下类型：integer（整数）、bulk string（字节串）、array（数组，元素也是这些类型）、nil、error。不支持直接返回 JSON 对象或浮点数（浮点会被截断为整数）。要返回复合对象，可以用 array：`return {rank, timestamp}`，Java 侧收到 `List<Object>`，按下标取值。也可以序列化成 JSON 字符串（bulk string）返回，Java 侧再反序列化，但增加了序列化开销。本项目只需要返回一个整数，编码最简单。

## Q15：Lua 脚本写 Redis 成功后，才去写 MySQL 的 RushRecord，两边数据会不一致吗？

会，且是真实的一致性缺口。Lua 成功后 Java 调 `rushRecordMapper.insert(record)` 写 MySQL，如果这步抛异常：Redis ZSET 有该用户，MySQL 没有记录。用户再次调 rush()，Lua 的 ZSCORE 返回有值 → 返回 -1（"已在队列中"），但查不到排队记录，行为矛盾。

**简单补偿**：catch DB 异常后 ZREM 撤回入队。

**Outbox 模式（生产级）**：在同一本地事务里同时写 rush_record 和 outbox，relay 服务扫描 outbox 做 Redis 操作，用 DB 的 ACID 代替分布式事务。

**↳ 追问：用 ZREM 撤回时，ZREM 本身也可能失败，这个问题能彻底解决吗？**

用 ZREM 撤回是"尽力而为"，ZREM 失败则留下孤立的 ZSET 记录，无法在这个方案内彻底解决。彻底解决需要换思路：以 MySQL 为唯一权威，定期对账——扫描 Redis ZSET 里的所有 member，对照 MySQL rush_record，找出"在 ZSET 但不在 MySQL"的记录，执行 ZREM 清理。这是"定期补偿"而非"实时补偿"，允许短暂不一致，最终对齐。或者彻底弃用 Redis ZSET 存排队状态，改为只在 MySQL 里存，用 SELECT COUNT FOR UPDATE 串行化，牺牲并发性能换强一致性。

## Q39：抢档期开放前，怎么做缓存预热？

1. **XXL-Job 定时任务**：提前扫描 `rushOpenTime` 在未来 10 分钟内的档期，将商家信息写入 Redis。
2. **ZSET 无需预先初始化**：第一次 ZADD 时 Redis 自动创建 key。
3. **服务启动时预热**：`ApplicationRunner` 加载当天近期有抢档计划的档期，防止刚重启就遇到高流量打穿缓存。

**↳ 追问：预热的数据写入 Redis 后，如果商家在开抢前修改了档期信息，缓存里还是旧数据，怎么处理？**

这是预热的固有问题：预热时间越早，开抢前被修改的概率越大。解法有两条：① 缩短预热窗口（比如从"提前 10 分钟"改为"提前 3 分钟"），减少修改窗口期；② 商家修改档期信息时，主动删除对应的 Redis 缓存 key（Cache Aside 写策略），下次有请求时重建缓存。两条可以结合：正常写流程走 Cache Aside 删缓存，预热只做首次填充，这样预热和正常写流程不冲突，预热的数据如果被修改会自动失效。

## Q40：热点数据怎么识别？抢档期场景里具体怎么做？

**通用方案（运行时探测）**：`redis-cli --hotkeys` 或应用层计数器，超阈值标记热点，做本地缓存或更短 TTL。

**项目方案（可预期热点主动预热）**：`rushOpenTime` 精确已知，直接利用时间信息主动预热，不需要运行时探测。运行时探测适合热点不可预期的场景（微博热搜、突发爆款）。

**↳ 追问：本地缓存（Caffeine）和 Redis 配合使用时，如果本地缓存的数据过期，但 Redis 里还有，会有几次网络往返？如果本地缓存数据和 Redis 数据不一致怎么处理？**

本地缓存 miss → 查 Redis（1次网络往返）→ 命中则直接写入本地缓存返回，共 1 次网络往返。如果 Redis 也 miss，再查 DB 并回填 Redis 和本地缓存。不一致的场景：Redis 数据更新（DB 写入后删 Redis key），但本地缓存还持有旧值，直到本地缓存 TTL 过期前都会返回旧数据。处理方式：① 本地缓存设短 TTL（如 5 秒），接受短暂不一致；② Redis 写入时广播失效事件（通过 MQ 或 Redis Pub/Sub），各实例收到事件后主动清除本地缓存；③ 部署实例数少时直接不用本地缓存，Redis 未成瓶颈不值得引入二级缓存的复杂度。

# 五、微服务架构（Gateway + Nacos + Dubbo/Feign）

## Q26：Gateway 和 Nginx 在项目里各自负责什么？为什么不让 Nginx 直接转发到微服务？

| | Nginx | Spring Cloud Gateway |
|---|---|---|
| 处理对象 | 静态文件 + SSL | `/api/**` 业务请求 |
| 路由依据 | 写死 IP:Port | Nacos 服务名，自动发现 |
| 新增实例 | 需改配置 + reload | 自动感知 |
| 扩展能力 | SSL、静态文件、高吞吐 | 鉴权过滤器、限流、热更新 |

**↳ 追问：Spring Cloud Gateway 底层用的是 Servlet 模型还是 WebFlux？为什么 API 网关适合用响应式模型？**

Spring Cloud Gateway 基于 WebFlux（Reactor + Netty），是非阻塞 IO 模型。API 网关的特点是：大量并发连接、每个请求主要时间花在等待下游服务响应（IO 等待）、本身几乎不做 CPU 密集计算。传统 Servlet 模型一连接一线程，高并发下线程数暴涨，线程切换和内存开销巨大；WebFlux 用少量线程（通常等于 CPU 核数）通过事件循环处理所有连接，线程不在 IO 等待期间阻塞，资源利用率极高，正好匹配 API 网关的访问模式。

---

## Q27：项目里 Dubbo RPC 和 OpenFeign 并存，选哪个的依据是什么？

- **Dubbo**：强依赖，失败直接终止业务——`getMerchantByUserId`（判断是否为商家）、`getBookingById`（校验预约状态）、`updateMerchantScore`（评分更新）。
- **Feign**：弱依赖，可降级返回空集合——`batchGetUsers`、`batchGetMerchants`（列表页批量拉用户信息）。

**↳ 追问：Dubbo 底层用什么协议？和 HTTP 相比性能上有什么区别？**

Dubbo 默认使用 Dubbo 协议（基于 TCP，Hessian2 二进制序列化）。对比 HTTP：① 协议头更紧凑，HTTP 头部是文本格式，每次携带大量 Header，Dubbo 协议头固定 16 字节；② 序列化更高效，Hessian2 是二进制序列化，比 JSON（文本）体积小、解析快；③ 长连接复用，Dubbo 在服务间维持长连接池，避免每次请求的 TCP 三次握手开销。代价是 Dubbo 协议不通用——前端浏览器不能直接调，只能用于服务间通信，所以必须经过 Gateway 层转换。Feign 走 HTTP，跨语言、跨系统兼容性更好，这是它适合外部暴露的原因。

---

## Q28：为什么服务间调用方向保持单向无环（DAG）？如果出现循环调用会怎样？

单向无环保证：任意服务出问题，只影响上游，不反向影响下游，故障半径可控。循环调用的问题：无限递归（A 调 B，B 调 A）、启动顺序死锁、级联雪崩（A 慢导致 B 等 A，B 也在等 A）。

**↳ 追问：如果业务上真的出现了双向依赖（A 需要 B 的数据，B 也需要 A 的数据），怎么破除循环而不丢失功能？**

有三种思路：① 事件驱动解耦——A 不直接调 B，而是发 MQ 事件，B 订阅处理后发另一个事件，A 再订阅。双方都只依赖 MQ，没有直接服务依赖；② 提取公共服务——把 A 和 B 都需要的数据放进第三个服务 C，A 和 B 都调 C，C 不调任何人；③ 重新划分服务边界——循环依赖往往说明这两个服务的职责没有划清，考虑把循环依赖的部分合并到同一个服务内处理，用本地方法调用代替跨服务调用。实践中最常用的是①（事件驱动）和③（合并边界）。

## Q29：评价提交时需要校验预约状态，mhp-social 怎么拿到 mhp-booking 的数据？

通过 Dubbo RPC。`RpcBookingService` 接口在 `mhp-common` 定义，Provider 在 `mhp-booking`，Consumer（mhp-social）注入 `@DubboReference`，走 Dubbo 协议点对点直连，不经过 Gateway。选 Dubbo 而不是 Feign：校验预约状态是前置条件，失败直接终止，无降级空间，强依赖语义。

**↳ 追问：Feign 和 Dubbo 调用失败（超时/宕机）时，默认行为分别是什么？Feign 的 fallback 怎么配？**

Feign 默认超时抛 `FeignException`，可以通过 `@FeignClient(fallback = XxxFallback.class)` 配置降级类，在降级类里返回默认值（如空列表）。Dubbo 默认超时 1 秒抛 `RpcException`，可以配置 `mock = "force:return null"` 做 mock 降级，或者 `@DubboReference(mock = "com.xxx.XxxMock")` 指定降级实现。本项目评价校验是强依赖，没有配置 fallback，失败直接抛异常回滚事务，让用户重试。批量拉用户信息（Feign）则配了降级：返回空 map，列表页展示时用"已注销"占位。

## Q16：评价创建的完整流程是什么？为什么要加 @Transactional？

```
① 取当前用户 ID
② Dubbo RPC → mhp-booking，验证预约存在且属于当前用户
③ 校验 status=3（已完成）
④ 校验未评价（一预约只评一次）
⑤ 写入 review 表
⑥ 全量重算该商家平均分
⑦ Dubbo RPC → mhp-account，更新 avgScore 和 reviewCount
⑧ mhp-account 删除商家缓存
```

`@Transactional` 覆盖步骤 ⑤~⑦：review 写入和评分更新必须同时成功或同时回滚。

**↳ 追问：@Transactional 能管住 Dubbo RPC 的远程调用吗？如果 mhp-account 宕机，review 写入会回滚吗？**

不能。`@Transactional` 只管本服务的数据库事务，Dubbo RPC 调用的是远程服务，完全独立的数据库连接和事务，不在 Spring 事务管理范围内。如果 mhp-account 宕机，Dubbo 调用抛 RpcException，Spring 捕获异常后回滚本服务的 review 写入，用户看到报错。这是"保守策略"——宁可让用户重试，也不让 review 和评分长期不一致。真正的跨服务强一致需要引入 Seata（TCC 模式），代价是每次都要协调多个服务的预留/提交/回滚，性能损耗和实现复杂度都很高，当前业务规模不值得。

---

## Q17：updateMerchantScore() 为什么每次全量重新算平均分，不做增量计算？

增量公式 `newAvg = (oldAvg * oldCount + newScore) / (oldCount + 1)` 在删评价、改评价时需要不同的公式，业务越复杂维护越难。全量计算从 DB 聚合，永远正确，商家评价通常千级以内，毫秒级耗时，代价可接受。这是"以简单换正确"的取舍。

**↳ 追问：如果某个商家积累了 10 万条评价，每次评价提交都全量 COUNT/AVG 会不会成为性能瓶颈？**

会。`SELECT AVG(score), COUNT(*) FROM review WHERE merchant_id = ?` 在 10 万行时需要全扫这 10 万行，即使走了 merchant_id 索引，聚合计算也要几十毫秒。优化方案：在 merchant 表冗余 `avg_score` 和 `review_count` 两列（项目已经这样做了），每次新增评价后增量更新这两列即可，不需要全量聚合。删评价和改评价时触发一次全量重算（低频操作，可接受），正常新增评价（高频操作）走增量计算。这是"读写分离"思想：把聚合结果缓存在主表列，牺牲少量写一致性换取读性能。

---

## Q18：评价写入后要更新 mhp-account 的评分，如果 mhp-account 宕机会怎样？

当前实现：Dubbo 调用失败抛异常，`@Transactional` 回滚 review 写入，用户报错。保守策略，宁可让用户重试也不让数据不一致。

更健壮方案：MQ 异步解耦，review 写入后发消息，account 消费后更新评分。account 宕机时消息积压，恢复后继续，最终一致。

**↳ 追问：改成 MQ 异步后，用户提交评价看到"成功"，但评分可能几秒后才更新，这段时间其他用户看到的还是旧评分，这种最终一致性能接受吗？有没有让用户感知不到延迟的办法？**

业务上可以接受：评分更新延迟几秒，但用户提交的评价本身立即可见（review 已写入 DB），体验影响极小。如果要让当前用户"感觉"评分已经更新，可以在前端做乐观更新：提交评价成功后，前端本地计算新的平均分并临时显示，不等后端异步更新完成。等下次真正刷新商家主页时，从 DB/缓存拿到最新值覆盖。这种前端乐观更新配合后端最终一致，是常见的用户体验优化手段。

# 六、实时消息推送与通知提醒（含社区 Feed 流 + RabbitMQ）

## Q19：聊天记录翻页为什么用游标分页（WHERE id < lastId），不用 LIMIT offset？

offset 分页：MySQL 扫描前 offset 行再丢弃，翻到第 N 页扫 N×size 行，性能线性退化。

游标分页：`WHERE id < lastId` 直接走索引定位，每次查询 O(log n)，无论翻到第几页性能一致。

**↳ 追问：游标分页有没有缺点？什么场景下反而应该用 offset 分页？**

游标分页的缺点：无法跳转到指定页（"第 100 页"），不支持随机翻页，只能向前或向后连续翻。如果 id 不连续（有删除记录），`id < lastId` 的结果页大小可能不稳定。offset 分页适合以下场景：管理后台列表（需要"跳到第 N 页"）、报表分页（页码对用户有意义）、数据量有限且不会超过几百页（offset 扫描代价可接受）。聊天记录用户只会往上翻，不需要跳页，游标分页完全契合。

---

## Q20：游标分页里怎么判断还有没有更多数据？为什么不做 COUNT 查询？

多查 1 条来判断：

```java
.last("LIMIT " + (size + 1))
boolean hasMore = messages.size() > size;
if (hasMore) messages = messages.subList(0, size);
```

避免了额外 `SELECT COUNT(*)`。COUNT 在大表上也要全扫或走索引统计，不快。

**↳ 追问：这里多查了 1 条数据，前端收到 size 条，但其实查了 size+1 条，这 1 条多余的数据会对性能有影响吗？**

几乎没有影响。多查 1 条是在已经走了索引定位到 lastId 位置之后，额外读取 1 条数据，代价是 1 次额外的索引查找 + 1 次回表，耗时在微秒级。相比之下，`SELECT COUNT(*)` 需要扫描满足条件的所有行来计数，对于百万级聊天记录表是毫秒级的额外 IO。两种方案代价相差 2~3 个数量级，多查 1 条是更优的选择。

---

## Q21：发消息时，DB 写入和 WebSocket 推送哪个先执行？顺序反过来会有什么问题？

先写 DB，后推送。如果先推送再写 DB：推送成功但 DB 失败，用户看到了消息，刷新后消息消失——"幻影消息"，体验极差。先写 DB 保证消息持久化，推送失败（用户离线）无所谓，上线后拉历史记录能看到，DB 是兜底。

**↳ 追问：如果 DB 写入成功但 WebSocket 推送失败（比如用户刚好断网），这条消息会丢失吗？用户怎么看到它？**

不会丢失。消息已存在 DB，WebSocket 推送仅是"实时通知"，是锦上添花。用户重新上线后，前端会触发一次历史消息拉取（`GET /api/message/history`），从 DB 拉取 lastId 之后的消息，这条"推送失败"的消息会出现在历史记录里。两者职责分离：DB 负责持久化（不丢失），WebSocket 负责实时性（可以失败）。这也是为什么项目选择"先写 DB 再推送"而不是"只推送"。

## Q22：WebSocket 连接认证为什么不能复用 SecurityConfig 里注册的 JwtAuthenticationFilter？

`JwtAuthenticationFilter` 继承 `OncePerRequestFilter`，是 Servlet Filter，只拦截 HTTP 请求。WebSocket 握手后的 STOMP 帧通过 WebSocket 协议传输，不经过 Servlet Filter 链。

`StompAuthChannelInterceptor` 拦截 CONNECT 命令，从 native header 取 token，调 `JwtUtil.parse()` 解析得 userId，`accessor.setUser(() -> userId)` 注入 Principal。`convertAndSendToUser(userId, ...)` 依赖这个 Principal 路由消息。

**↳ 追问：`accessor.setUser(() -> userId)` 这里存的 userId 是 Long 还是 String？`convertAndSendToUser` 是怎么用它路由到正确会话的？**

`setUser` 接受 `java.security.Principal`（函数式接口），`getName()` 返回 String，所以存的是 `userId.toString()`。`convertAndSendToUser(userId, destination, payload)` 内部会查找所有 WebSocket 会话，找到 `Principal.getName().equals(userId)` 的会话，将消息投递到 `/user/{userId}/queue/notify`（Spring 自动拼接）。如果同一用户开了多个 Tab，多个会话的 Principal.getName() 都等于该 userId，消息会被投递到所有会话——即多端同步收到通知。

## Q30：帖子点赞为什么用 Redis 记录而不直接写 MySQL？setIfAbsent 怎么实现 like/unlike 切换？

```java
String key = "post:likes:" + postId + ":" + userId;
Boolean firstLike = stringRedisTemplate.opsForValue()
        .setIfAbsent(key, "1", 24 * 365, TimeUnit.HOURS);
if (Boolean.TRUE.equals(firstLike)) {
    // key 不存在 → 首次点赞 → 计数 +1
    lambdaUpdate()...setSql("like_count = like_count + 1").update();
} else {
    // key 已存在 → 已点赞，此次取消 → 删 key + 计数 -1
    stringRedisTemplate.delete(key);
    lambdaUpdate()...setSql("like_count = GREATEST(like_count - 1, 0)").update();
}
```

**↳ 追问：setIfAbsent + MySQL 计数 +1 这两步不是原子的，如果 setIfAbsent 成功但 MySQL 更新失败，会怎样？**

会出现状态不一致：Redis 说"已点赞"（key 存在），但 MySQL 的 like_count 没有增加。用户看到的点赞数不变，但再次点击会触发"取消点赞"逻辑。这是已知的一致性缺口。完善的方案有两条：① 把点赞事件写入 MQ，消费者串行处理"写 Redis + 更新 MySQL"，保证顺序和可重试；② 不在 MySQL 列存 like_count 冗余，而是查询时动态从 Redis 统计（SCAN key pattern），但这在 key 量大时性能差。项目当前规模下这个概率极低，可以接受，但生产级应当用 MQ 方案。

## Q31：Feed 流有"关注的商家"和"全部"两个入口，用的是推模式还是拉模式？为什么？

项目用**拉模式**：查 Feed 时先查关注的商家 id 列表，再 `WHERE merchant_id IN (...)` 拉帖子。

选拉模式的原因：商家（内容生产者）数量远小于用户（消费者），每人关注的商家通常几十个，IN 子句数据量可控。推模式写放大严重——热门商家发帖要给几万粉丝各写一条收件箱记录。

**↳ 追问：如果某个用户关注了 500 个商家，IN 子句有 500 个 ID，MySQL 会怎么处理这个查询？会走索引吗？**

MySQL 会对 IN 子句里的 500 个值分别走 `merchant_id` 索引查找，找到所有匹配行后做合并和排序（通常需要 filesort，除非有 `(merchant_id, create_time)` 联合索引）。500 个 id 的 IN 查询在 MySQL 里是可接受的，但如果关注数增长到几千，`IN` 子句变长，索引查找次数线性增加，需要考虑优化：① 建 `(merchant_id, create_time DESC)` 联合索引，避免 filesort；② 超过一定关注数阈值的用户，异步预生成 Feed 列表存 Redis，查询时直接读（混合推拉模式）。

## Q48：帖子图片上传是怎么实现的？为什么不经过后端服务器？

```
① GET /api/post/upload-token → 后端签发 UploadToken（含 bucket、TTL 1h、文件大小限制）
② 前端直接 POST 图片 + token 到七牛云 CDN 节点
③ 七牛云返回文件 key
④ 前端把 key + 帖子内容提交到 POST /api/post
⑤ 后端存 key，查询时拼接 CDN 域名返回完整 URL
```

不经过后端：节省带宽、释放 Tomcat 连接、后端无状态便于扩容。

**↳ 追问：前端拿到 upload token 后可以上传任意文件到七牛云，怎么防止滥用（比如上传可执行文件、超大文件）？**

Token 里可以内置限制：① 文件类型限制——设置 `mimeLimit` 参数，只允许 `image/jpeg,image/png`，七牛云在接收文件时校验 MIME 类型，不符合则拒绝；② 文件大小限制——设置 `fsizeLimit` 参数，超过限制直接拒绝上传；③ Key 前缀策略——Token 里固定 key 前缀（如 `user/{userId}/`），用户只能上传到自己的目录下，无法覆盖他人文件；④ 短 TTL——Token 有效期 1 小时，过期后无法上传。后端存 key 时还可以校验 key 格式是否符合预期，防止前端伪造其他 bucket 的 key 注入。

## Q32：项目里为什么用 MQ 做预约通知，而不是 booking 直接调 social 推 WebSocket？

同步 Feign 调用的问题：social 宕机时 confirm() 抛异常，核心业务被辅助功能拖垮，两个不相关功能强耦合。

MQ 解决三个问题：**解耦**（booking 不关心 social 是否在线）、**异步**（塞进 MQ 即返回，< 1ms）、**可靠**（MQ 持久化，social 宕机恢复后补发）。

**↳ 追问：你说 MQ 能"削峰"，这里的通知场景有削峰的需要吗？削峰、解耦、异步三者分别解决什么问题，不要混用？**

通知场景主要用到**解耦**和**异步**，削峰需求不强。三者各自解决的问题：① **异步**：把慢操作移出请求链路，降低 RT。比如发通知不影响预约确认结果，可以异步做；② **解耦**：生产者和消费者独立部署、独立扩展，互不依赖。social 宕机不影响 booking，这是本场景的主要诉求；③ **削峰**：消费者按自己的速度消费，不被瞬时流量压垮。抢档期场景最典型——开放瞬间大量请求写入 MQ，消费者平滑处理，DB 不被直接冲击。三个作用是独立的，同一个 MQ 可以同时发挥多个作用，但引入 MQ 的核心理由要说清楚是哪个。

## Q41：通知走 MQ 异步推送，和同步 Feign 调用 social 相比，RT 为什么更低？

同步调用 RT = 整条链路 IO 之和：DB 写入 + Feign 网络 RTT + social 推 WebSocket。

MQ 异步 RT = DB 写入 + 塞进 MQ（< 1ms），通知发送完全异步。

核心思路：把"不影响结果正确性"的操作移出请求链路。

**↳ 追问：RT 降低了，但通知的"实时性"也降低了——用户可能在确认后几十毫秒才收到通知，这是否可接受？如果要同时保证低 RT 和高实时性，有什么方案？**

几十毫秒的延迟在 WebSocket 通知场景完全可接受——用户体感上"几乎是实时"。真正有问题的是 social 服务压力大时消息积压，延迟可能到秒级。如果要同时保证低 RT 和高实时性：① 优先保证消费者的处理速度，消费者不做耗时操作（只推 WebSocket，不做复杂业务），消费速度快则延迟低；② 消费者水平扩展，增加 Consumer 实例数消化积压；③ 用异步化的本地线程池代替 MQ（只在单服务内），把通知推送提交到线程池异步执行，RT 降低的同时没有网络传输延迟——但这牺牲了解耦，social 宕机时通知就真丢了。

## Q42：confirm() 先改 DB 状态再发 MQ，如果 MQ 发送失败，通知丢了怎么办？Outbox 模式怎么设计？

当前缺陷：DB 状态改为 2 后，MQ 发送失败，通知静默丢失，无补偿。

**Outbox 模式：**

```
本地事务内：
  UPDATE booking SET status=2 WHERE id=?
  INSERT INTO outbox (payload, sent=false)

独立 relay 服务：
  SELECT * FROM outbox WHERE sent=false
  → rabbitTemplate.send(...)
  → UPDATE outbox SET sent=true WHERE id=?
```

DB 的 ACID 保证"业务写"和"消息登记"同时成功或失败。relay 宕机重启后扫描 outbox 补发。

**↳ 追问：Outbox relay 服务如果重启，从 outbox 表扫描重发时，已经发成功的消息可能被重发（at-least-once），Consumer 侧怎么保证不重复处理？**

这正是 Outbox 模式要求 Consumer 侧必须幂等的原因。本项目 Consumer 已经用 Redis SET NX 做了幂等去重（见 Q35）：每条消息有唯一 msgId，`setIfAbsent` 保证同一 msgId 只处理一次。Outbox relay 重发时，消息的 msgId 不变（从 outbox 表的 payload 字段里带过来），Consumer 收到重复消息时 `setIfAbsent` 返回 false，直接 ACK 跳过。两者配合：Outbox 保证"至少一次投递"，Consumer 幂等保证"最多一次处理"，合起来实现"恰好一次"的业务效果。

## Q33：RabbitMQ 的 Exchange、Queue、Binding 三者是什么关系？项目的 RabbitConfig 是怎么配置的？

```
Producer → publish(exchange, routingKey)
              ↓ 按 Binding 的 bindingKey 匹配
Exchange  →  Queue（存储消息）→ Consumer
```

项目拓扑：Topic Exchange `schedule.exchange` → `notify.queue`（绑定 `notify.#`）→ 死信 → `notify.dead.queue`。

为什么 booking 和 social 都声明同一拓扑：RabbitMQ 幂等声明，重复声明参数相同的资源不报错，保证两个服务都不依赖对方先启动。

**↳ 追问：Topic Exchange 的 `*` 和 `#` 有什么区别？`notify.#` 能匹配 routingKey 为 `notify` 的消息吗（没有点，只有 notify）？**

`*` 匹配恰好一个词（词以 `.` 分隔），`#` 匹配零个或多个词。所以：`notify.#` 能匹配 `notify`（零个词）、`notify.booking`（一个词）、`notify.booking.confirmed`（两个词）。`notify.*` 则只匹配 `notify.booking` 这种恰好一个词的 routingKey，不匹配 `notify`（无词）或 `notify.booking.confirmed`（两个词）。项目用 `notify.#` 是为了未来可以扩展子类型（`notify.booking_confirmed`、`notify.rush_created`），一个绑定规则统一捕获所有通知类型，不需要为每种类型单独建 Binding。

## Q34：手动 ACK 和自动 ACK 的区别是什么？项目为什么选手动 ACK？

自动 ACK：消息出队瞬间确认，Consumer 崩溃来不及处理则消息永久丢失。手动 ACK：处理完后调 `channel.basicAck()` 确认，处理前崩溃则消息重新入队。

```java
channel.basicAck(tag, false);            // 成功确认
channel.basicNack(tag, false, false);    // 失败，requeue=false → 死信
```

`requeue=false`：业务逻辑错误时无限重试没意义，进死信队列留存供运维分析。

**↳ 追问：prefetch（QoS）是什么？为什么推荐在 Consumer 里设置 prefetch=1？设太大有什么问题？**

prefetch 控制 Consumer 最多同时持有多少条未 ACK 的消息（即一次性预取数量）。设 prefetch=1 的效果：Consumer 每次只拿 1 条，处理并 ACK 后再拿下一条，消息在多个 Consumer 实例间均匀分发（Round Robin）。设 prefetch=250 的问题：某个 Consumer 实例一次性拿走 250 条，即使它处理很慢（比如处理的是耗时操作），其他快的 Consumer 实例也只能等它 ACK 完这 250 条才能拿到新消息，导致消息分布不均，快实例空闲、慢实例积压。prefetch=1 牺牲一点网络往返（每条消息都要 ACK 才取下一条），换取消息在 Consumer 间的公平分发。

## Q35：消费者怎么保证同一条消息不被重复处理？（幂等性）

Redis SET NX 去重：

```java
Boolean isNew = stringRedisTemplate.opsForValue()
    .setIfAbsent("msg:processed:" + msg.getMsgId(), "1", 24, TimeUnit.HOURS);
if (Boolean.FALSE.equals(isNew)) {
    channel.basicAck(tag, false);  // 已处理过，跳过
    return;
}
// 首次处理，继续业务逻辑

// 失败时必须删 key，允许下次重试
stringRedisTemplate.delete(idempotentKey);
```

**↳ 追问：幂等 key 的 TTL 设 24 小时，如果同一消息在 25 小时后被重新投递（比如死信手动重投），key 已过期，还会重复处理吗？有没有更强的保证？**

会重复处理。24 小时 TTL 假设消息不会在 24 小时后被重投，对正常的 At-Least-Once 重试场景足够，但死信手动重投可能间隔很久。更强的保证：把 msgId 持久化到 MySQL 的 `processed_messages` 表（`msgId, process_time`），Consumer 处理前先查这张表。DB 的数据不会因 TTL 过期，可以永久去重。代价是每次消费都多一次 DB 读（可以加缓存）。另一种思路：让消费的业务操作本身幂等，不依赖外部去重——比如 WebSocket 推送相同消息，用户只是看到两条一样的通知，影响可接受。是否需要强幂等取决于重复消费的业务影响有多大。

---

## Q36：如何保证消息从生产到消费全链路不丢失？三个环节分别怎么保证？

```
Producer ──①── Exchange/Queue ──②── MQ宕机 ──③── Consumer
```

① **Publisher Confirm**：MQ 收到后回调 `confirmCallback`（`ack=true`）。项目目前只打日志，未实现重发（已知缺口）。

② **MQ 持久化**：Exchange + Queue `durable(true)`，消息 `deliveryMode=PERSISTENT`（Spring AMQP 默认）。

③ **Consumer 手动 ACK**：处理完才 ACK，处理前 crash 则重投。

**↳ 追问：publisher-confirm-type 设为 `correlated` 而不是 `simple`，两者有什么区别？**

`simple` 模式：整个 Channel 级别的确认，`waitForConfirms()` 会阻塞直到 Channel 上所有消息都被确认，无法区分哪条消息被确认哪条失败，不适合高并发场景。`correlated` 模式：每条消息绑定独立的 `CorrelationData`（携带消息 ID 等元信息），Broker 确认/拒绝时回调对应的 `confirmCallback`，精确知道哪条消息成功哪条失败，可以针对失败消息单独重发。项目用 `correlated` 是为了能精确重发失败消息，即使目前重发逻辑还没实现（只打日志），框架层面已经具备了精确重发的能力。

## Q37：死信队列是什么？项目里是怎么设计的？

死信触发条件：① `basicNack` + `requeue=false`；② 消息超过 TTL；③ Queue 达到最大长度。

```
notify.queue basicNack(requeue=false)
    ↓ x-dead-letter-exchange
schedule.dead.exchange → notify.dead.queue
```

死信队列价值：消息不丢、问题可追溯、支持人工重投。

**↳ 追问：死信队列里的消息如何实现自动延迟重试（比如失败后等 5 分钟再重试），而不是人工干预？**

利用 TTL + 死信的组合实现延迟队列：① 创建一个"等待队列"，不绑定 Consumer，设置 `x-message-ttl=300000`（5 分钟）和 `x-dead-letter-exchange=正常交换机`；② 消息处理失败后 `nack` 到这个等待队列（而不是直接进真正的死信）；③ 等待队列的消息 5 分钟后 TTL 过期，变成死信，自动路由回正常交换机 → 正常队列，重新被 Consumer 消费。这是 RabbitMQ 实现延迟重试的经典方案，无需插件。如果需要指数退避（第 1 次 1 分钟，第 2 次 5 分钟，第 3 次 30 分钟），可以建多个不同 TTL 的等待队列，Consumer 根据重试次数选择不同的等待队列路由。

## Q38：`RUSH_CREATED` 和 `RUSH_REMINDER` 为什么在消费端做 fan-out，而不是生产端发多条消息？

消费端 fan-out：MQSender 只发 1 条（带 merchantId），NotifyConsumer 收到后查 follow 表，遍历关注者逐一推 WebSocket。

选消费端的原因：① follow 数据在 mhp-social，booking 服务查它需要跨服务调用，消费端在 social 直接查本地表；② 只需确认 1 条消息，Publisher Confirm 更简单；③ 大 V 10 万粉丝时不会把 10 万条消息一次性打进 Queue。

**↳ 追问：消费端 fan-out 时，如果一个商家有 10 万关注者，消费者要循环推 10 万次 WebSocket，这个消费者会成为瓶颈吗？怎么优化？**

会。单个消费者串行推 10 万次 WebSocket，每次网络 RTT 算 1ms，光是推送就需要 100 秒，严重积压 MQ。优化方案分两层：① 当前服务内：把推送任务提交到线程池（`ExecutorService`），消费者只负责从 follow 表拿 userId 列表并提交任务，推送并行执行，整体耗时从"串行总和"降为"最慢一次"；② 横向扩展：把单条"商家发帖"消息转化为多条"给用户推送"消息，分发到多个 Consumer 实例并行消费——即在消费端做一次二级 fan-out，但这引入了消息数量膨胀问题，需要权衡。对于当前社区规模，线程池方案已足够。

# 七、按需搜索推荐（Elasticsearch + Function Score）

## Function Score 是什么？是 ES 提供的功能吗？

`function_score` 是 Elasticsearch 的内置查询类型，在原始 BM25 分基础上用自定义函数做二次加工：

```
最终得分 = BM25_score × (avgScore × 1.2 + log1p(reviewCount) × 0.5)
           ↑ boost_mode=multiply     ↑ score_mode=sum
```

无关键词时 BM25 给所有文档相同的 1.0，等价于纯按业务指标排序。

---

## Q6：商家搜索为什么不用 MySQL LIKE，要引入 Elasticsearch？

MySQL `LIKE '%keyword%'` 的问题：① `%` 开头无法走索引，全表扫描；② 只有是否匹配，无相关度分数；③ 不支持拼音（搜"zn"找不到"妆娘"）。

ES 解决：倒排索引快速定位，IK 分词器 + 拼音子字段支持中文和拼音，BM25 算相关度分天然排序。

**↳ 追问：ES 的倒排索引具体是什么结构？和 MySQL 的 B+ 树索引相比，各自适合什么查询类型？**

倒排索引的结构：词项字典（Term Dictionary，B 树或 FST）→ 词项对应的文档列表（Posting List，压缩存储文档 id、词频、位置）。查询"妆娘"时：在词项字典找到"妆娘"，O(log n) 直接拿到包含该词的所有文档 id，再做评分排序。B+ 树适合范围查询和等值查询（`WHERE id BETWEEN 1 AND 100`、`WHERE city = '北京'`），有序存储支持高效范围扫描。倒排索引适合全文检索（`MATCH '妆娘'`），但不支持高效范围查询（倒排 Posting List 无序，范围查询需要合并多个列表）。两者互补：MySQL 做精确的结构化查询，ES 做全文搜索和相关度排序。

---

## Q7：搜索排序是怎么设计的？为什么不直接 sort(avgScore) 而是用 Function Score？

有关键词时应相关度优先但不完全无视商家质量，无关键词时应纯按质量排序。`sort` 无法同时兼顾两种场景且会覆盖 BM25 分。

Function Score 统一：`最终得分 = BM25_score × 业务质量分`。无关键词时 BM25=1.0，等价于纯业务排序；有关键词时两者融合。一套算法覆盖两种场景。

**↳ 追问：BM25 是什么算法？它和 TF-IDF 相比改进了什么？**

TF-IDF：词频（TF）× 逆文档频率（IDF）。问题：① TF 无上限，词出现 1000 次比 100 次得分高 10 倍，但实际相关度不是线性的；② 长文档因为包含更多词而得分虚高。BM25 的改进：① 对 TF 做饱和处理（通过参数 k1 控制），词出现次数超过一定量后边际收益递减，避免"词频堆砌"刷高分；② 引入文档长度归一化（参数 b），长文档里的词不会因为文档长就被过度惩罚。实际效果 BM25 > TF-IDF，ES 5.0 起默认用 BM25 替代 TF-IDF。

## Q8：Function Score 里为什么 reviewCount 用 log1p 处理，avgScore 直接线性？

`reviewCount` 量级差异巨大（0~10000），直接加权让大户碾压新商家。`log1p(x) = ln(1+x)` 边际递减，从 0→100 贡献大，从 1000→10000 贡献小，合理反映规模效应。

`avgScore` 固定在 1~5，量级均匀，直接线性加权即可。`missing` 值：avgScore=3.0（中等），reviewCount=0。

**↳ 追问：log1p 的 "1p" 是什么意思？为什么不直接用 log(reviewCount)，而要 log(1 + reviewCount)？**

"1p" 是 "1 plus" 的缩写，即 `log(1 + x)`。直接用 `log(reviewCount)` 的问题：当 reviewCount=0 时，`log(0)` 是负无穷，会导致算分变成负无穷，使没有评价的新商家永远排在最末。`log1p(0) = log(1) = 0`，没有评价的商家得 0 分，参与正常排序而不是被降到末尾。这也是为什么 ES 的 `field_value_factor` 里 modifier 专门提供了 `log1p` 选项——这是处理"从 0 开始计数的数值字段"的标准做法。

## Q9：ES 里的数据是怎么和 MySQL 保持同步的？为什么不在 Service 层双写？

双写问题：两次写操作不在同一事务，MySQL 成功但 ES 失败时数据不一致；每个写商家数据的地方都要加 ES 写入，侵入性强、容易漏写。

Canal 方案：监听 MySQL binlog，数据库层感知所有变更：`MySQL binlog → Canal Server → CanalSyncService → ES`。保证 MySQL 写成功，Canal 保证 ES 最终一致，延迟毫秒~秒级。

Canal 还解决了级联更新：用户改昵称时感知 user 表变更，自动更新 ES 里商家的 nickname/avatar。

**↳ 追问：Canal 是怎么感知 MySQL binlog 的？它伪装成了什么？为什么需要配置 server-id？**

Canal 把自己伪装成 MySQL 从库（Replica），向 MySQL 主库发送 `COM_REGISTER_SLAVE` 命令注册，然后像真正的从库一样通过 `COM_BINLOG_DUMP` 请求 binlog 数据流，主库正常推送 binlog。MySQL 的主从复制协议要求每个从库有唯一的 `server-id`（32位整数），用于标识节点，防止复制循环（A→B→A）。Canal 配置的 `server-id` 必须在整个 MySQL 复制拓扑中唯一，如果设为 0 或与已有从库重复，MySQL 会拒绝注册。这也是为什么 CLAUDE.md 里特别提到"server-id=0 会被 MySQL 拒绝"——0 是 MySQL 的保留值。

## Q10：CanalSyncService 里的 ack/rollback 是什么意思？处理失败了会怎样？

```java
Message message = connector.getWithoutAck(100);  // 拉取但不推进游标
long batchId = message.getId();
try {
    for (Entry entry : message.getEntries()) { processEntry(entry); }
    connector.ack(batchId);        // 游标前移
} catch (Exception e) {
    connector.rollback(batchId);   // 游标不动，下次重发
}
```

rollback 后整批重发，ES 操作必须幂等。`save()` 是 ES 的 index 操作，相同 id 完整覆盖，天然幂等。

**↳ 追问：rollback 会把整批 100 条重发，如果是第 50 条失败，前 49 条已经成功写入 ES，重发后这 49 条会被重复写入，会有数据问题吗？**

不会有数据问题，但有性能开销。ES 的 index 操作幂等：相同 id 的文档再次 index 会完整覆盖，无论执行多少次，最终状态与只执行一次完全相同，不会产生重复文档。代价是这 49 条会被重复处理，增加 ES 的写负载。如果频繁失败（比如第 50 条总是失败），会造成 Canal 卡死在这个 batchId、前 49 条被反复重写的问题。此时应该在 processEntry 内部捕获个别条目的异常，记录失败的 entry 但不让整批 rollback，成功处理其他条目后再 ack。这是"跳过坏消息"策略，代价是失败的那条记录会丢失同步，需要人工补偿。

## Q11：用户创建评价后，ES 里的 avgScore 和 reviewCount 是怎么更新的？

```
ReviewServiceImpl.create()
  → 全量重算平均分
  → Dubbo RPC 写回 MySQL merchant 表（avg_score, review_count）
  → Canal 感知 merchant 表变更
  → handleMerchantChange() 重查 DB 拿完整行
  → merchantEsRepository.save(doc)
```

为什么不用 binlog 的 afterColumns 直接构建文档：ROW 格式 binlog 的 afterColumns 只记录**本次改动的列**，未改动列不出现，直接用会把其他字段（nickname、city）覆盖为 null。

**↳ 追问：Canal 是异步的，评价提交后 ES 里的评分什么时候能更新？这段时间用户搜索到的是旧评分，会有问题吗？如果要求评价后搜索结果立刻反映新评分，怎么做？**

Canal 延迟通常毫秒到秒级，用户刚提交评价，短暂看到旧评分是正常体验，不影响业务。如果要立刻反映，有两条路：① 在评价创建成功后，除了写 MySQL，同时直接调 ES SDK 更新该商家的 avgScore 字段（`UpdateRequest`，只更新这一个字段，不是全量覆盖）——这是双写，引入了 MySQL 和 ES 不一致的风险，但实时性最好；② 接受延迟，在前端做乐观更新：提交评价成功后，前端本地临时显示新的预估评分，等下次真正刷新商家详情页时从后端拿到最新值。项目当前搜索排序对评分变化不敏感（几秒延迟不影响搜索结果位置），Canal 异步方案已足够。
