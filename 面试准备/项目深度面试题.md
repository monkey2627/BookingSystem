# 一、商家主页缓存（Cache Aside + 防三缓）

## Q1：商家主页为什么要加缓存？直接查数据库有什么问题？

商家主页是高频读、低频写的场景：用户反复查看同一商家详情，但商家信息（简介、价格、评分）很少变动。每次直接查 MySQL 有两个代价：一是 DB IO 延迟（几十毫秒），在高并发下会造成明显的响应时延；二是数据库连接数有限，热门商家的流量会打满连接池，影响其他业务。

加 Redis 缓存后，命中率高的情况下从几十毫秒降到个位数毫秒，且对数据库完全透明。

---
## 什么是cache aside（旁路缓存模式）

最常用的缓存设计模式，Redis 业务里最主流方案。核心思想：**缓存和数据库分开，业务代码自己维护缓存，缓存不介入数据库读写，数据库是真实数据源**。

> 数据库：权威数据源；缓存：副本，仅做加速。

### 1. 读流程
1. 先读 **Cache**
2. ✅命中：直接返回缓存数据
3. ❌未命中：去查 **DB**，把查到的数据**回写到缓存**，再返回给调用方
### 2. 写流程
> Cache‑Aside 有两种写策略：**先更数据库，再删缓存（推荐）**；先更新缓存（不推荐）。
#### 更新数据库 → 删除缓存（不是更新缓存）
1. 更新数据库
2. **删除缓存 key**（而不是去 set 新值到缓存）

> 为什么是**删除缓存，而不是更新缓存**？
> 并发场景下两个写线程，如果更新缓存，会出现缓存旧值覆盖新值；删除缓存，下次读请求会自动加载最新 DB 数据到缓存，避免脏缓存。

#### ❌不推荐：先更新缓存再更新数据库
极易出现缓存新值、数据库旧值，数据永久不一致。

#### ❌不推荐：先删缓存，再更新数据库
会出现经典并发问题：
> 线程A删缓存，还没写完DB；线程B过来读，缓存缺失读旧DB数据，回填旧缓存；之后A才把DB更新完成。**缓存永久脏数据**。

---
### 3. 并发问题与缺陷
#### 问题1：读写并发下短暂脏数据
> 线程A写：更新DB成功，准备删缓存；
> 线程B读：刚好此时缓存还没删，读到旧缓存。

这是**短暂不一致**，缓存马上就会被删掉，下一次读就恢复。大部分业务可以接受。
如果要缓解：给缓存设置**TTL过期时间**，兜底脏缓存。

#### 问题2：缓存删除失败
DB更新成功，但是删Redis网络异常失败 → 缓存一直是旧数据。
解决：
1. 给缓存强制TTL兜底
2. 消息队列重试删除缓存（异步重试）

### 4. Cache‑Aside 优缺点
**优点**
- 逻辑简单，业务可控；缓存只是旁路，数据库始终可靠；
- 适合读多写少绝大多数业务；
- 缓存失效只由业务代码控制，框架无侵入。

**缺点**
- 会有短暂数据不一致；
- 写操作会触发缓存失效，下一次读发生**缓存穿透（回源DB）**；
- 需要业务代码手动维护缓存，没有自动同步。

### 5. 和其他缓存模式对比简单区分
1. **Cache‑Aside（旁路）**：业务代码管缓存，DB为主源。（最常用）
2. **Read‑Through（读穿透）**：缓存组件封装，读缓存缺失由缓存组件自己读DB，业务只访问缓存。Java一些缓存框架实现。
3. **Write‑Through（写穿透）**：写的时候缓存组件同步写缓存+写DB，业务只写缓存。
4. **Write‑Back（写回）**：只写缓存，缓存异步刷DB，性能高，宕机丢数据。

> 生产 Redis 几乎都是 **Cache‑Aside，DB更新完成后删除缓存 + TTL兜底**。

### 补充面试高频点
1. Cache‑Aside 为什么**删缓存而不是更新缓存**？
   多线程写场景，更新缓存会发生请求时序错乱导致缓存保存旧值；删除缓存，由后续读请求加载最新数据。
2. 先删缓存再更新数据库会发生什么？
   会出现：读请求读到旧数据回填缓存，造成永久脏缓存。
3. 如何解决删除缓存失败？
- 设置TTL兜底
- MQ异步重试删除缓存
4. 数据不一致怎么解决？
   业务容忍短暂不一致；强一致性场景不适合Cache‑Aside。
## Q2：你说防缓存穿透、击穿、雪崩，分别指什么问题？你是怎么解决的？

这三个问题发生在不同的场景：

**穿透**：请求的 key 在 Redis 和 DB 都不存在，每次都打到 DB，攻击者可以构造大量不存在的 merchantId 把 DB 打垮。

解法：不存在的 id 也写入缓存，值是空字符串，TTL 2分钟（短，防止合法商家注册后数据长时间不显示）。下次请求命中这个空值哨兵直接抛 `MERCHANT_NOT_FOUND`，不再查 DB。

**击穿**：某个热门 key 缓存刚好过期，瞬间大量并发请求同时发现缓存缺失，全部穿透到 DB，造成 DB 瞬时压力峰值（雪崩的单 key 版本）。

解法：Redisson 分布式锁 `lock:merchant:{id}`，只有一个线程能查 DB 并重建缓存，其他线程在锁上排队。拿到锁后还要**再查一次缓存**（DCL），因为在等锁期间前一个线程可能已经写好缓存了。

**雪崩**：大量 key 同时过期（比如启动时批量预热、或者所有 key 用了相同 TTL），同时大量请求打到 DB。

解法：TTL 加随机偏移 `25 + random.nextInt(11)` = 25~35 分钟随机，让不同 key 的过期时间错开，避免集中过期。

完整代码路径：`MerchantServiceImpl.getDetail()`。

## Q3：DCL 双重检查，第一次检查和第二次检查的作用分别是什么？

```java
// 第一次（无锁快路径）
String cached = stringRedisTemplate.opsForValue().get(cacheKey);
if (cached != null) { return ...; }

// 加锁
lock.lock();

// 第二次（有锁，保证最新状态）
cached = stringRedisTemplate.opsForValue().get(cacheKey);
if (cached != null) { return ...; }

// 真正查 DB
```

**第一次**：无锁，所有请求都能并发执行，缓存命中时直接返回，不抢锁，性能最优。

**第二次**：在拿到锁之后、查 DB 之前再查一次。原因是：可能有多个线程同时通过了第一次检查（缓存都是 null），之后它们排队等锁，第一个线程查 DB 并写了缓存，后面的线程拿到锁后如果不再查，就会重复查 DB 并覆盖缓存，白白浪费。DCL 第二次检查让后面的线程直接返回第一个线程写好的缓存。

## Q4：缓存更新为什么选"更新 DB → 删除缓存"，而不是"更新 DB → 更新缓存"？

更新缓存看起来直观，但有数据一致性问题：

```
线程A：更新 DB（新值=5）
线程B：更新 DB（新值=6）
线程B：更新缓存（写入6）
线程A：更新缓存（写入5）← 旧值覆盖了新值！
```

DB 存的是 6，缓存存的是 5，不一致。

删除缓存没有覆盖问题：下次请求发现缓存缺失，从 DB 读最新值并重建，天然拿到最新数据。代价是缓存重建期间有一次穿透，但结合分布式锁防击穿，只有一个线程查 DB，可以接受。

---

### Q5：这个方案有没有缺点？能做到强一致性吗？

不能做到强一致性，存在一个短暂的不一致窗口：

```
线程A：读缓存，miss
线程A：查 DB，拿到旧值（新值还没提交）
线程B：更新 DB，提交新值
线程B：删除缓存
线程A：写缓存，写入旧值  ← 此时缓存存了旧值，但 DB 已经是新值
```

这个窗口极短（几毫秒）。对于商家详情这种场景，轻微的延迟一致性完全可接受——用户看到的评分稍微滞后几毫秒不影响体验。

如果要求强一致性，需要引入分布式事务（2PC/TCC）或者直接不缓存，代价远超收益。

## 二、商家搜索（Elasticsearch + Function Score）

### Q6：商家搜索为什么不用 MySQL，要引入 Elasticsearch？

MySQL 的 `LIKE '%keyword%'` 有三个问题：

1. **全表扫描**：`%` 开头无法走索引，百万数据量下耗时秒级。
2. **无相关度**：LIKE 只返回是否匹配，无法按"keyword 和商家有多相关"排序，搜索体验差。
3. **不支持拼音**：搜索"zhuangniang"找不到"妆娘"，搜索"zn"也找不到。

ES 解决了这三个问题：倒排索引快速定位，IK 分词器+拼音分析器支持中文和拼音，BM25 算法计算相关度分数，天然支持按相关度排序。

---

### Q7：搜索排序是怎么设计的？为什么不直接用 `sort` 而是用 Function Score？

**无关键词**的情况（纯浏览）：应该按商家质量（评分、接单量）排序，相关度没有意义。

**有关键词**的情况（有搜索意图）：应该相关度优先，但完全无视商家质量也不好——搜"妆娘"出来的第一个是差评累累的商家，用户体验差。

用 `sort` 的问题：两种场景需要不同的 sort 策略，切换逻辑复杂，且 `sort` 强制覆盖相关度，有关键词时就无法利用 BM25 分数。

**Function Score** 统一解决：

```
最终得分 = BM25相关度分 × (avgScore × 1.2 + log(1 + reviewCount) × 0.5)
```

无关键词时 BM25 对所有文档给相同的 1.0 分，等价于纯按业务因子排序；有关键词时相关度和业务质量共同影响排名，二者加权融合。一套算法覆盖两种场景。

---

### Q8：Function Score 里为什么 reviewCount 用 log1p，avgScore 不用？

`reviewCount` 的问题是**量级差异**：有的商家 100 条评价，有的 10000 条，直接加权会让接单大户完全碾压新商家。`log1p(x) = log(1+x)` 是边际递减函数——从 0 增长到 100 贡献大，从 1000 增长到 10000 贡献很小——合理反映规模效应同时给新商家机会。

`avgScore` 取值范围固定在 1~5，量级本身就均匀，直接线性加权即可。

另外，`avgScore` 的 `missing` 值设为 3.0（中等分），让没有评价的新商家也能参与排序，不至于永远排在末尾；`reviewCount` 的 `missing` 值设为 0，新商家不凭空获得接单量加分。

---

### Q9：ES 里的数据是怎么保持和 MySQL 同步的？双写会有什么问题？

走的是 **Canal CDC**，不是双写。

双写方案（Service 层同时写 MySQL 和 ES）的问题：两次写操作不在一个事务内，MySQL 成功但 ES 失败时数据就不一致了，而且需要在每个写商家数据的地方都加 ES 写入，侵入性强、容易漏写。

Canal 方案：监听 MySQL binlog，从数据库层面感知所有变更，不依赖业务代码：

```
MySQL binlog → Canal Server → CanalSyncService（后台线程） → ES
```

只需要保证 MySQL 写成功，Canal 保证 ES 最终一致。代价是有轻微延迟（毫秒~秒级），对商家搜索完全可接受。

Canal 还解决了一个难题：商家 ES 文档里的 `nickname`/`avatar` 来自 user 表，用户改昵称时 Canal 感知 `user` 表变更，找到对应商家并更新 ES doc，这是双写方案很难优雅处理的级联更新。

---

### Q10：Canal 的 ack/rollback 机制是什么？和 RabbitMQ 的手动 ACK 有什么相似之处？

Canal 类似消息队列，维护一个消费游标（offset）：

- `getWithoutAck(100)`：拉取最多 100 条 binlog 事件，不自动提交游标
- `connector.ack(batchId)`：本批处理成功，提交游标，Canal 记录"已消费到这里"
- `connector.rollback(batchId)`：处理失败，回滚游标，下次拉取时会重新从这批开始

和 RabbitMQ 手动 ACK 一样：**先处理，后确认**，处理失败时不确认，保证消息不丢。区别是 RabbitMQ 处理单条消息，Canal 处理一批（batch）事件。

`rollback` 之后下次重新消费这批 binlog，需要保证 ES 操作幂等（相同 id 的 `save()` 会覆盖，天然幂等）。

## 三、抢档期（Lua + Redis ZSET）

### Q11：抢档期为什么要用 Lua 脚本？不能用事务或者 Redisson 锁吗？

**分布式锁方案**：可行，但性能差。每个用户抢档期都要串行等锁，高并发下大量用户排队，吞吐量约等于单线程。Lua 脚本在 Redis 单线程内原子执行，不需要锁，天然无竞争。

**Redis 事务（MULTI/EXEC）方案**：MULTI/EXEC 期间不能读中间值——`ZSCORE` 的结果在 EXEC 之前拿不到，无法根据它来决定是否 `ZADD`，所以 `WATCH + 乐观锁` 才能实现条件写，但 WATCH 失败需要重试，还是不如 Lua 简洁。

**Lua 方案**：Redis 单线程执行 Lua 脚本，ZSCORE + ZCARD + ZADD 三步作为原子整体，任何时刻只有一个脚本在跑，没有并发问题，且可以在脚本内读中间结果来做条件判断：

```lua
local existScore = redis.call('ZSCORE', KEYS[1], ARGV[1])
if existScore then return -1 end                          -- 已入队
if redis.call('ZCARD', KEYS[1]) >= tonumber(ARGV[3]) then return 0 end  -- 队满
redis.call('ZADD', KEYS[1], tonumber(ARGV[2]), ARGV[1])
return redis.call('ZRANK', KEYS[1], ARGV[1]) + 1         -- 返回名次
```

---

### Q12：抢档期用 ZSET 而不是 LIST，为什么？

ZSET（有序集合）的每个成员有一个 score，这里用时间戳毫秒作为 score，实现"先来先得"：

| 操作 | LIST | ZSET |
|------|------|------|
| 去重（一人只能入队一次）| 需要 LPOS，O(n) | ZSCORE 判断，O(log n) |
| 查询排名 | 需要遍历，O(n) | ZRANK，O(log n) |
| 先来先得顺序 | 插入顺序，但无法防止重复 | score=时间戳，天然有序 |

ZRANK 返回的排名就是用户的队列位置，直接展示"您排在第 N 位"，无需额外计算。

---

### Q13：Lua 脚本返回 -1/0/正整数，这个编码为什么这样设计？

返回值同时承载"成功/失败"和"成功时的数据"两个语义：

- `-1`：已入队（业务正常情况，不是系统错误）
- `0`：队列已满（业务正常情况）
- `>0`：排队名次，从 1 开始（ZRANK 返回 0-based，脚本内 +1 转成用户友好的 1-based）

Java 侧只需判断返回值落在哪个区间，不需要额外字段。选这三个值而不是用字符串，是因为 Lua 返回整数比返回 table 要简单，Redis execute 的 `Long` 类型也更好处理。

---

### Q14：Redis 记录排队，MySQL 也要写一条 RushRecord，两边数据会不一致吗？

会有短暂不一致，但可接受：Lua 脚本成功后，Java 侧才异步写 MySQL。中间极短时间内 Redis 有记录但 MySQL 没有。

这个时间窗口极短（毫秒级），且不影响核心功能：排队依赖 Redis ZSET（实时性强），MySQL 记录用于持久化和后续查询。如果 MySQL 写入失败（概率极低），Redis 里有记录，用户的排队位置不受影响，MySQL 可以通过补偿机制（定时任务对账）修复。

如果要强一致，可以走 MQ：Lua 成功后发消息，消费者写 MySQL，ACK 机制保证最终一致，但复杂度显著上升，不符合当前场景需要。

## 四、评价创建（跨服务调用 + 事务）

### Q15：评价创建的完整流程是什么？为什么要加 @Transactional？

完整流程（`ReviewServiceImpl.create()`）：

```
① 从 ThreadLocal 取当前用户 ID
② Dubbo RPC 调 mhp-booking（RpcBookingService.getBookingById），验证预约存在且属于当前用户
③ 检查预约 status=3（已完成），只有完成的预约可评价
④ 检查是否已评价（一个预约只能评一次）
⑤ 写入 review 表
⑥ 重新聚合该商家所有评价，计算新的平均分
⑦ Dubbo RPC 调 mhp-account（RpcMerchantService.updateMerchantScore），更新商家 avgScore 和 reviewCount
⑧ mhp-account 删除商家缓存（缓存 key: merchant:info:{id}），触发下次访问重建
```

注意：mhp-social → mhp-booking、mhp-social → mhp-account 的跨服务调用走的是 **Dubbo RPC**（`@DubboReference`），不是 OpenFeign。只有查用户展示信息（昵称/头像）这类轻量查询才走 Feign。

加 `@Transactional` 覆盖步骤 ⑤~⑦：review 写入和商家评分更新必须同时成功或同时回滚。如果 review 写入成功但评分更新失败（比如 mhp-account 宕机），下次查商家详情评分就对不上实际评价，数据不一致。

**局限**：`@Transactional` 管不了 Dubbo RPC 的远程事务——mhp-account 的 DB 更新不在这个事务里。真正的强一致需要分布式事务（Seata），这里用的是最终一致：review 写入成功后，account 更新即使短时失败，可以触发补偿重试，评分最终会对齐。

---

### Q16：商家评分为什么每次全量重新计算，不做增量计算？

增量计算的方式：`newAvg = (oldAvg * oldCount + newScore) / (oldCount + 1)`。

看起来简单，但有一个隐患：如果有评价被删除或修改，增量公式就失效了——需要不同的增量公式。随着业务变复杂（删评价、修改评价、投诉撤销评价），增量逻辑越来越难维护。

全量计算直接从 DB 聚合，永远正确，无论中间发生什么操作。代价是每次多一次 `SELECT ... WHERE merchant_id=?`，但商家评价数量通常在千级以内，查询耗时毫秒级，完全可接受。这是"以简单换正确"的取舍。

---

### Q17：Review 和评分更新涉及两个微服务，如果 mhp-account 宕机会怎样？

当前实现：Dubbo RPC 调用失败会抛异常，`@Transactional` 回滚 review 写入，用户看到报错。

这是**保守策略**——宁可让用户重试，也不让 review 和评分长时间不一致。对当前业务规模可以接受。

更健壮的方案是 **MQ 异步解耦**：review 写入成功后，发一条"新评价"消息到 RabbitMQ，mhp-account 消费后更新评分。即使 account 短暂宕机，消息持久化在 MQ 里，恢复后继续消费，最终一致。代价是引入 MQ，架构复杂度上升，这是项目的待优化点。

## 五、消息系统（游标分页 + WebSocket 实时推送）

### Q18：消息历史记录为什么用游标分页，不用 offset 分页？

offset 分页（`LIMIT offset, size`）的问题：MySQL 在执行时会从头扫描 `offset` 行然后丢弃，翻到第 1000 页时实际扫了 10000 行，随着翻页数增大性能线性退化。

游标分页（`WHERE id < lastId LIMIT size`）：`id` 上有索引，直接定位到 `lastId` 的位置，每次查询都是 O(log n) 的索引查找，无论翻到第几页性能都一样。

聊天记录场景额外适合游标分页：用户从最新消息向上翻，是连续的"上一批"操作，id 单调递减，天然契合 `id < lastId` 的游标模式。

---

### Q19：怎么判断是否还有更多消息，不做 COUNT 查询？

查 `size + 1` 条：

```java
.last("LIMIT " + (size + 1))

boolean hasMore = messages.size() > size;
if (hasMore) messages = messages.subList(0, size);  // 截掉多查的那条
```

如果实际返回了 `size + 1` 条，说明还有更多；只返回 `<= size` 条，说明已到末尾。

避免了额外的 `SELECT COUNT(*)` 查询（COUNT 在大表上也不快）。代价是每次多查一条，可以忽略不计。

---

### Q20：发消息时，WebSocket 推送和 DB 写入的顺序是什么？为什么？

**先写 DB，后推送**：

```java
save(message);                                    // 先持久化
messagingTemplate.convertAndSendToUser(..., vo);  // 后推送
```

如果先推送再写 DB，推送成功但 DB 写入失败，用户看到了消息，但刷新后消息不见了——消息"幻影"，体验非常差。

先写 DB 保证消息一定持久化。推送失败（用户离线）无所谓，用户上线后拉历史记录能看到这条消息，DB 是兜底。

---

### Q21：WebSocket 连接时为什么不能用 Spring MVC 的 `SaInterceptor` 验证 token？

Spring MVC 的 `HandlerInterceptor`（包括 `SaInterceptor`）只拦截 HTTP 请求——WebSocket 握手时走 HTTP Upgrade，之后所有 STOMP 帧通过 WebSocket 协议传输，不经过 Spring MVC 的拦截器链。

STOMP 的 `CONNECT` 帧是连接升级后客户端发的第一帧，在这里验证 token 是最自然的位置。`StompAuthChannelInterceptor` 拦截 CONNECT 命令，从 native header 取 `token`，调 `StpUtil.getLoginIdByToken()` 验证（不依赖 ThreadLocal，线程安全），然后 `accessor.setUser(() -> userId)` 注入 Principal。

后续 `convertAndSendToUser(userId, ...)` 依赖这个 Principal 来路由到正确的会话，所以这里必须把 userId 注入为 Principal。

## 六、用户认证（Sa-Token + ThreadLocal）

### Q22：Sa-Token 登录的完整流程是什么？token 存在哪里？

```java
StpUtil.login(user.getId());       // ① 生成 token，写入 Redis
vo.setToken(StpUtil.getTokenValue()); // ② 返回 token 给客户端
```

**登录时**：Sa-Token 生成一个 UUID token，在 Redis 里写入 `satoken:login:token:{token} → userId`（默认 TTL 30天）。把 token 返回给前端，前端存到 localStorage。

**后续请求**：前端在 Header `token` 字段带上 token。`SaInterceptor` 拦截，从 Header 取 token，查 Redis 得到 userId，写入当前线程的 ThreadLocal。

**Service 层**：`StpUtil.getLoginIdAsLong()` 从 ThreadLocal 读 userId，O(1)，无 IO。

**请求结束**：`afterCompletion()` 清除 ThreadLocal，防止线程归还到线程池后数据残留。

---

### Q23：为什么 token 放 Header 而不放 Cookie？

Cookie 默认跨域受限（SameSite=Strict），跨域请求需要额外配置，且 Cookie 是浏览器自动携带的，有 CSRF 风险——攻击者诱导用户访问恶意页面，浏览器自动带上 Cookie，伪造合法请求。

Header token 需要 JavaScript 主动读取和设置，CSRF 攻击无法控制 JS 行为（同源策略），天然防 CSRF。移动端也不依赖 Cookie，逻辑更统一。

代价是 JS 必须能访问 localStorage（`HttpOnly` Cookie 无法被 JS 读），XSS 攻击可以窃取 token，所以必须严格防 XSS。

---

### Q24：MD5 存密码有什么安全问题？项目里有没有加盐？

MD5 的问题：MD5 是确定性函数，相同明文永远生成相同哈希。攻击者可以预先算好常见密码的 MD5（彩虹表），一旦数据库泄露，直接查表反推明文。

项目里用的是 Hutool 的 `SecureUtil.md5(password)`，没有加盐。这是一个已知的安全缺陷——如果密码是"123456"，MD5 是固定值，查彩虹表秒破。

生产环境应该用 **BCrypt**：内置随机盐，相同密码每次生成的哈希不同，且计算成本可调（work factor），有效对抗彩虹表和暴力破解。Spring Security 内置 `BCryptPasswordEncoder`，迁移成本低。这是项目的待优化项。

## 七、微服务架构（Gateway + Nacos + OpenFeign）

### Q25：Gateway 和 Nginx 在这个项目里各自做什么？职责怎么分工？

| | Nginx | Spring Cloud Gateway |
|---|---|---|
| 处理对象 | 前端静态文件（HTML/JS/CSS）+ SSL | `/api/**` 业务请求 |
| 路由依据 | 写死 IP:Port | Nacos 服务名（`lb://mhp-account`），自动服务发现 |
| 新增实例 | 需改 upstream 配置 + reload | Nacos 自动感知，无需改动 |
| 扩展能力 | SSL 终止、静态文件缓存、高吞吐 | 鉴权过滤器、限流、路由规则热更新 |

请求链路：

```
用户 → Nginx (443/80)
  ├── 静态文件 → 直接返回 dist/
  └── /api/** → proxy_pass → Gateway:80
                  → 按路径匹配分发到 mhp-account/booking/social
```

分工原则：Nginx 做基础设施层（SSL、静态文件），Gateway 做应用层（业务路由、过滤器）。两层各司其职，Gateway 专注于服务发现和业务逻辑，不处理 SSL，性能更好。

---

### Q26：OpenFeign 调用失败会怎样？有没有重试或降级？

当前项目没有配置 Feign 重试和降级（Sentinel 的 `@SentinelResource` 注解已加，但 QPS 阈值未配置，限流规则未生效）。

Feign 默认失败直接抛 `FeignException`，传播到 Controller，被 `GlobalExceptionHandler` 捕获，返回 500 错误。

**重试**：Feign 有 `Retryer` 接口，默认不重试。对于幂等的 GET 请求（如查用户信息）可以加重试；对于写操作（如更新评分）不应重试（可能重复执行）。

**降级**：应该为每个 FeignClient 写 `FallbackFactory`，网络抖动时返回兜底数据（比如查用户失败返回"未知用户"），而不是让整个接口 500。这是项目的待完善点。

---

### Q27：为什么 OpenFeign 调用方向是单向无环的？如果循环调用会有什么问题？

当前调用方向：
```
mhp-booking → mhp-account
mhp-social  → mhp-account
mhp-social  → mhp-booking
```

如果 mhp-account 也调 mhp-booking，形成环：`booking → account → booking → ...`，可能导致：

1. **调用链无限递归**：A 调 B，B 调 A，直到线程栈溢出。即使有限深，也会导致不必要的网络往返，延迟叠加。
2. **启动顺序依赖**：A 依赖 B，B 也依赖 A，谁先启动都找不到对方，可能导致服务启动失败。
3. **级联雪崩**：A 慢，B 等 A，A 又在等 B（如果 B 也调了 A），全部超时。

单向无环（DAG）保证：任意服务出问题，只影响"上游"依赖它的服务，不会反向影响"下游"服务，故障半径可控。

---

### Q28：评价服务需要验证预约，社区服务怎么拿到预约数据？

通过 **Dubbo RPC**。`RpcBookingService` 接口定义在 `mhp-common`，Provider 在 `mhp-booking`，Consumer（`mhp-social`）通过 `@DubboReference` 注入：

```java
@DubboReference(version = "1.0.0")
private RpcBookingService rpcBookingService;
```

调用 `rpcBookingService.getBookingById(orderId)` 拿到 `BookingDTO`，走 Dubbo 协议点对点直连，不经过 Gateway。

**项目里 Dubbo 和 Feign 并存，选择依据是业务语义**：

`RpcBookingService.java` 注释里说得很清楚——"mhp-social 在发起评价/投诉前必须校验预约状态，**失败则整个业务终止，无降级空间**，适合 RPC 强调用"。Dubbo 用于权限校验、状态校验这类"失败直接终止"的强依赖（`getMerchantByUserId` 判断是否为商家、`getBookingById` 判断预约状态）；Feign 用于批量数据拉取（`batchGetUsers`、`batchGetMerchants`）这类可以降级返回空的弱依赖。

这个划分在 `mhp-booking` 里同样适用：`BookingServiceImpl` 和 `ScheduleServiceImpl` 都同时注入了 `AccountFeignClient`（Feign，批量查）和 `@DubboReference RpcMerchantService`（Dubbo，权限校验）。

## 八、点赞设计与 Feed 流

### Q29：点赞用 Redis 记录而不是 MySQL，是什么考虑？

点赞有两个查询需求：一是查"用户 A 有没有点赞帖子 B"，二是查"帖子 B 的总点赞数"。

如果用 MySQL 记录每条点赞（insert/delete），高并发下频繁写 MySQL 压力大，且查是否点赞需要 `SELECT COUNT(*) WHERE post_id=? AND user_id=?`，有索引也要走 B+ 树。

Redis 方案实现真正的切换（like/unlike）：

```java
String key = "post:likes:" + postId + ":" + userId;
Boolean firstLike = stringRedisTemplate.opsForValue()
        .setIfAbsent(key, "1", 24 * 365, TimeUnit.HOURS);
if (Boolean.TRUE.equals(firstLike)) {
    // key 不存在 → 首次点赞 → 写 key + 计数 +1
    lambdaUpdate().eq(Post::getId, postId)
            .setSql("like_count = like_count + 1").update();
} else {
    // key 已存在 → 已点赞，此次操作是取消 → 删 key + 计数 -1
    stringRedisTemplate.delete(key);
    lambdaUpdate().eq(Post::getId, postId)
            .setSql("like_count = GREATEST(like_count - 1, 0)").update();
}
```

`setIfAbsent` 是原子操作，返回 true/false 同时完成状态判断和写入，不存在并发下重复点赞的问题。`GREATEST(like_count - 1, 0)` 防止计数出现负值。

查是否点赞（列表展示时）：`stringRedisTemplate.hasKey(key)`，O(1)。

**缺点**：Redis key 数量随帖子数和用户数增长为 O(n×m)，长期来看需要考虑内存压力，可改用 SETNX + EXPIRE 配合定期清理旧帖子数据。

---

### Q30：帖子的 Feed 流有两种模式（关注列表 vs 全量），这个设计有什么权衡？

**推模式（Fan-out）**：用户发帖时，主动推送给所有关注者的收件箱。查 Feed 时直接读自己的收件箱，查询快。缺点是写放大——粉丝多的大V发一条帖子要写入百万个收件箱，延迟高且存储成本大。

**拉模式（Fan-in）**：用户查 Feed 时，实时拉取关注列表所有人的帖子并合并排序。读时有计算，但写只写一份，存储成本低。

项目用的是**拉模式**：

```java
// followedFeed：拉取关注的商家 ID 列表，然后 WHERE merchant_id IN (...)
List<Long> merchantIds = followMapper.selectList(...).stream()
        .map(Follow::getMerchantId).collect(Collectors.toList());
```

选拉模式的原因：Cosplay 社区的商家关注数通常不大（几十~几百），合并排序成本可控；而且商家（生产者）数量远小于粉丝（消费者）数量，推模式会造成严重的写放大。
