# 预约超时取消流程 — 面试模拟

> 基于项目真实代码（BookingJobHandler、BookingServiceImpl、MQSender、NotifyConsumer）。

---

## 完整流程图

```
① 用户发起预约
   → Redisson 分布式锁（booking:create:{userId}:{scheduleId}）
   → DCL 双重检查档期状态
   → 写库 status=0（待确认）
   → 档期置为"已预约"（status=1）

② XXL-Job 每 5 分钟扫描（cancelTimeoutBookingJob）
   → 查 status=1 且超过 30 分钟的预约（LIMIT 100）
   → 批量置 status=4（已取消）
   → 释放档期回 status=0（空闲）

③ RabbitMQ 异步通知（Topic 交换机 schedule.exchange）
   → MQSender.send() → routing key: notify.{type}
   → 匹配绑定 key: notify.# → notify.queue

④ WebSocket 实时推送
   → NotifyConsumer 消费
   → Redis SET NX 幂等校验（msg:processed:{msgId}，24h）
   → 手动 ACK
   → convertAndSendToUser → /user/queue/notify → 浏览器
```

## Q&A 模拟

---

### Q1：整体介绍一下这个流程

用户发起预约后，商家需要在规定时间内确认。如果超时不操作，预约自动取消并释放档期。整个流程分四段：创建预约（分布式锁防并发）→ 定时扫描超时（XXL-Job）→ MQ 异步通知 → WebSocket 实时推送。

---

### Q2：XXL-Job 扫的是 status=1，但 status=1 是"待付款"当前未使用，这个 Job 实际扫不到任何数据？

对，这是**预留设计**。当前 `confirm()` 直接把 status 从 0 跳到 2，不经过 1，所以 Job 运行不会取消任何预约。

这个 Job 是为将来接入支付宝/微信支付预留的：
```
未来流程：
status=0（待确认）→ 商家确认 → status=1（待付款）→ 用户付款 → status=2（已定档）
```
届时 Job 才会发挥作用。对 status=0 超时取消的逻辑目前是项目的**待完善点**。

---

### Q3：创建预约为什么要用分布式锁？用数据库唯一索引不就够了？

唯一索引可以兜底防止数据重复，但管不了**档期状态的并发竞争**。

创建预约要同时做两件事：检查档期是否空闲 + 把档期置为"已预约"。这是"检查再操作"的经典竞态——两个请求可能同时通过检查，都认为档期空闲，然后都去占用。唯一索引管不了档期状态字段。

另外，唯一索引冲突会抛数据库异常，用户体验差；分布式锁可以在应用层给出"操作频繁，请稍后再试"的友好提示。

锁的粒度设为 `booking:create:{userId}:{scheduleId}`，同一用户对同一档期的并发请求才互斥，不影响其他档期的预约。

---

### Q4：tryLock(3, 30, TimeUnit.SECONDS) 两个时间分别是什么意思？

```java
lock.tryLock(3, 30, TimeUnit.SECONDS)
//           ↑   ↑
//        等待时间  持锁时间（lease time）
```

**等待 3 秒**：锁被别人持有时最多等 3 秒。设 3 秒而不是 0，是因为持锁方通常很快（数据库写入毫秒级），短暂等待可以让请求成功而不是直接拒绝。

**持锁 30 秒**：拿到锁后最多持有 30 秒自动释放。防止进程崩溃导致死锁——JVM 挂了锁不会永久占用，30 秒后自动释放。30 秒远大于正常业务执行时间（几十毫秒），不会误释放。

> **注意**：设了 lease time，Redisson 的 watchdog 自动续期机制就**不生效**。
> 不设 lease time（传 -1）才会启用 watchdog 每 10 秒续期一次。

---

### Q5：拿到锁之后为什么要重查一次 schedule？

这是 **DCL（双重检查锁定）** 模式。

```java
// 加锁前查了一次（无锁，可能过时）
Schedule schedule = scheduleMapper.selectById(dto.getScheduleId());

lock.tryLock(...);  // 等锁期间状态可能已被其他线程改变

// 加锁后再查一次（有锁，保证最新状态）
schedule = scheduleMapper.selectById(dto.getScheduleId());
if (schedule.getStatus() != 0) {
    throw new BusinessException(ResultCode.SCHEDULE_NOT_AVAILABLE);
}
```

加锁前的查询只是快速初步校验，在等锁期间档期可能已被别人预约。拿到锁后重查，保证基于最新状态做决策。

---

### Q6：通知为什么走 RabbitMQ，直接 Feign 调 social 推 WebSocket 不行吗？

可以跑通，但有三个问题：

| 问题 | Feign 直调 | RabbitMQ |
|------|-----------|----------|
| 耦合性 | booking 依赖 social，social 宕机连核心业务都失败 | 完全解耦，social 宕机不影响 booking |
| 可靠性 | 调用失败消息丢失，无持久化 | 消息持久化到磁盘，social 重启后仍能消费 |
| 性能 | 同步等待通知发完才返回响应 | 异步，发完消息立即返回，不阻塞主流程 |

### Q7：NotifyConsumer 为什么要手动 ACK？

自动 ACK 的问题：消息出队瞬间即确认，如果后续 WebSocket 推送失败，消息已经没了，通知丢失。

手动 ACK 精确控制确认时机：

```java
try {
    messagingTemplate.convertAndSendToUser(...);  // 推送
    channel.basicAck(tag, false);                 // 成功才确认出队
} catch (Exception e) {
    stringRedisTemplate.delete(idempotentKey);    // 删幂等 key，允许重试
    channel.basicNack(tag, false, false);          // 失败进死信队列（requeue=false）
}
```

---

### Q8：为什么 RabbitMQ 会重复投递？怎么处理？

RabbitMQ 是 **At-Least-Once** 语义，保证至少投递一次，不保证恰好一次。

重复投递场景：消费者处理完消息、推送成功，正准备发 ACK，网络闪断。Broker 没收到 ACK，认为失败，重新投递。结果同一条消息被处理两次，用户收到两条相同通知。

解法：**Redis SET NX 幂等**，key 是 `msg:processed:{msgId}`，24 小时过期。

```java
Boolean isNew = stringRedisTemplate.opsForValue()
        .setIfAbsent(idempotentKey, "1", 24, TimeUnit.HOURS);
if (Boolean.FALSE.equals(isNew)) {
    channel.basicAck(tag, false);  // 重复消息，直接 ACK 跳过
    return;
}
```

第一次 SET NX 成功正常处理；第二次返回 false，直接 ACK 跳过，不重复推送。

---

### Q9：NACK 之后 requeue=false，消息去死信队列有什么用？

死信队列（DLQ）是消息的"最后兜底"，进去的消息不会丢：

1. **监控告警**：死信有积压说明有消息持续失败，触发报警让人工介入
2. **排查原因**：查看死信内容，分析哪类推送失败
3. **人工补发**：修复问题后把死信重新投递

不用 `requeue=true` 是因为：推送失败大概率是系统性故障（如 WebSocket 全挂），立即重入队会无限循环失败，加剧压力。进死信等人工处理更稳妥。

---

### Q10：XXL-Job 每次 LIMIT 100，为什么加这个限制？

防止**数据库压力峰值**。

如果系统宕机几小时，积压了大量超时预约，一次性 UPDATE 几千行会导致数据库 IO 飙升、锁表时间过长，影响其他正常请求。

LIMIT 100 每次小批量处理，单次执行快（毫秒级），让出数据库资源给其他业务。积压数据分多轮处理完，系统平稳。这是**以时间换稳定性**的典型权衡。
