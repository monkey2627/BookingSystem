# SpringCloud 基础概念

> 结合 MHP 项目（mhp-account / mhp-booking / mhp-social / mhp-gateway）整理。

---

## 一、架构演进

### 单体架构
所有功能模块都在一个项目中，打成一个 jar/war 运行。

**优点**：开发简单、部署简单、本地调用性能高。

**缺点**：
- 项目越来越大，编译/启动越来越慢
- 任何一个模块出 bug，整个服务不可用
- 无法对某个模块单独扩容（比如只有搜索压力大，但整个应用都要横向扩展）
- 技术栈被锁死，所有模块只能用同一套语言和框架

### 集群架构
同一套单体应用部署多个实例，通过 Nginx 负载均衡分发请求。

解决了**高并发**问题，但没有解决模块耦合问题。数据库也可以做集群（读写分离、分库分表）。

### 分布式 / 微服务架构
将单体应用**按业务拆分**成多个独立的小服务，每个服务：
- 独立部署、独立扩容
- 有自己的数据库
- 通过网络互相调用（HTTP/gRPC/MQ）

**MHP 项目的拆分**：
```
mhp-account  — 用户 + 商家（User/Merchant）
mhp-booking  — 档期 + 预约（Schedule/Booking）
mhp-social   — 社区（Post/Review/Message/Follow）
mhp-gateway  — API 网关（统一入口）
```

**微服务带来的新问题**（这些问题催生了 Spring Cloud 的各个组件）：

| 问题 | Spring Cloud 解决方案 |
|------|----------------------|
| 服务 A 怎么找到服务 B 的地址？ | Nacos（注册中心） |
| 所有服务的配置怎么统一管理？ | Nacos（配置中心） |
| A 调用 B 的代码怎么写？ | OpenFeign（声明式 HTTP 客户端） |
| B 挂了 A 不能跟着崩 | Sentinel（熔断降级） |
| 所有请求的统一入口 + 鉴权 | Spring Cloud Gateway |
| 一次请求跨多个服务，怎么追踪？ | SkyWalking / Zipkin（链路追踪） |

## 二、CAP 定理

分布式系统中，以下三个特性**最多只能同时满足两个**：

| 特性 | 说明 |
|------|------|
| **C** onsistency（一致性） | 所有节点在同一时刻看到的数据相同 |
| **A** vailability（可用性） | 每个请求都能得到响应（不保证最新数据） |
| **P** artition Tolerance（分区容错） | 网络分区（部分节点之间无法通信）时系统仍然运行 |

网络分区在分布式系统中**必然会发生**（P 必须保证），所以只能在 C 和 A 之间选择：

**CP（一致性 > 可用性）**：网络分区时拒绝服务，保证数据一致。典型：ZooKeeper、Nacos 集群模式。

**AP（可用性 > 一致性）**：网络分区时仍然提供服务，但数据可能不一致，最终一致。典型：Eureka、Nacos 单机模式。

**Nacos 的选择**：
- 服务注册（临时实例）：AP 模式，优先可用（某个节点挂了，其余节点仍提供服务）
- 服务注册（持久实例）：CP 模式，优先一致
- 配置中心：CP 模式（配置数据必须一致）

## 三、服务注册与发现

### 没有注册中心时

```
服务 A 调用服务 B：
  A 需要知道 B 的 IP:Port（硬编码在配置文件）
  B 扩容/缩容/重启换 IP → A 的配置要跟着改 → 不可维护
```

### 有注册中心后

```
服务 B 启动 → 向 Nacos 注册自己的 IP:Port
服务 A 调用 B → 先问 Nacos "B 在哪里？" → 得到 B 的实例列表 → 负载均衡选一个 → 发请求
```

**心跳机制**：
- 服务启动后，每隔 5 秒向 Nacos 发一次心跳
- Nacos 超过 15 秒没收到心跳 → 标记实例为不健康
- 超过 30 秒 → 从注册列表删除
- 好处：不需要人工下线服务，自动感知

**实例缓存**：
- 服务 A 获取到实例列表后，在**本地缓存**一份
- 即使 Nacos 短暂宕机，A 还是能用缓存的地址调用 B
- Nacos 恢复后，缓存自动更新

## 四、负载均衡

服务 A 调用服务 B 时，Nacos 可能返回 B 的多个实例（B1、B2、B3），需要选一个。

**Spring Cloud LoadBalancer**（Spring Cloud 官方，替代了已废弃的 Ribbon）

常见策略：
- **轮询（RoundRobin，默认）**：B1 → B2 → B3 → B1 → ...
- **随机（Random）**：随机选一个实例

**配置负载均衡策略**（application.yaml）：
```yaml
spring:
  cloud:
    loadbalancer:
      configurations: random  # 改成随机策略
```

## 五、Spring Cloud 组件一览

```
Spring Cloud（顶层框架，定义规范）
├── 服务注册发现：Nacos / Eureka / Consul
├── 配置中心：   Nacos Config / Spring Cloud Config
├── 远程调用：   OpenFeign（声明式）/ RestTemplate（手动）
├── 负载均衡：   Spring Cloud LoadBalancer（取代 Ribbon）
├── API 网关：   Spring Cloud Gateway（响应式）/ Zuul（Servlet）
├── 熔断降级：   Sentinel（Alibaba）/ Resilience4j
└── 链路追踪：   SkyWalking / Zipkin / Sleuth
```

**版本对应关系（重要）**：

| Spring Boot | Spring Cloud | Spring Cloud Alibaba |
|-------------|--------------|----------------------|
| 3.2.x       | 2023.0.x     | 2023.0.x             |
| 3.1.x       | 2022.0.x     | 2022.0.x             |
| 2.7.x       | 2021.0.x     | 2021.0.x             |

版本不匹配是最常见的 SpringCloud 报错原因。

## 六、服务间通信方式

### 同步调用（HTTP / gRPC）

```
调用方 → 等待 → 被调用方返回 → 调用方继续
```

- **优点**：简单，实时拿到结果
- **缺点**：调用链长时一个服务慢影响整条链路；强依赖，被调用方挂了调用方也报错
- **实现**：OpenFeign（本项目使用）

### 异步调用（消息队列）

```
调用方 → 发消息到 MQ → 立即返回
                           ↓
                       被调用方消费消息（异步）
```

- **优点**：解耦，调用方不等待；被调用方挂了消息不丢，恢复后继续消费
- **缺点**：不能实时拿到结果；消息中间件是额外的基础设施
- **实现**：RabbitMQ（本项目用于：预约状态变更 → 推送 WebSocket 通知）

**本项目的调用方向（OpenFeign 同步调用）**：
```
mhp-booking → mhp-account（验证商家身份、获取用户信息）
mhp-social  → mhp-account（获取用户/商家展示信息）
mhp-social  → mhp-booking（Review/Complaint 校验预约状态）

异步（MQ）：
mhp-booking（发消息）→ RabbitMQ → mhp-social（消费 → WebSocket 推送）
```

## 七、分布式事务问题

微服务场景下，一次业务操作可能跨多个服务的数据库：

```
用户下预约单：
  mhp-booking：INSERT booking
  mhp-account：UPDATE merchant.review_count（评价后）
  mhp-social：  INSERT review
```

这三个操作分属三个数据库，传统的 ACID 事务无法跨库保证。

**常见解决方案**：

| 方案 | 说明 | 本项目 |
|------|------|--------|
| Seata（AT 模式） | 两阶段提交，强一致 | 未使用（复杂度高） |
| TCC（Try-Confirm-Cancel） | 业务代码实现补偿 | 未使用 |
| 最终一致性（MQ + 幂等） | 靠消息队列保证最终一致 | 部分使用 |
| 人工补偿 | 定时任务扫描不一致数据 | `BookingJobHandler` |

本项目选择**不引入分布式事务**：业务流程是单向的（预约 → 评价），通过 OpenFeign 单向调用 + MQ 异步消息保证数据最终一致，用 XXL-Job 定时任务处理超时异常状态。

## 八、服务部署架构

```
用户请求
  ↓
Nginx（443/80）
  ├── location /          → dist/ 静态文件（Vue 打包产物）
  └── location /api/      → proxy_pass → Spring Cloud Gateway:80
                                            ↓（Nacos 服务发现 + 负载均衡）
                               ┌────────────────────────────┐
                               │ mhp-account:8081           │
                               │ mhp-booking:8082           │
                               │ mhp-social:8083（含 WS）   │
                               └────────────────────────────┘
                                            ↓
                               MySQL / Redis / RabbitMQ / ES / Canal
```

**Nginx vs Gateway 分工**：

| | Nginx | Spring Cloud Gateway |
|---|---|---|
| 角色 | 基础设施层 | 应用层 |
| 路由目标 | 写死 IP:Port | 服务名（Nacos 动态发现） |
| 新增实例 | 需改配置 + reload | 自动感知 |
| 自定义逻辑 | Lua 脚本 | Java Filter（鉴权、限流、日志）|
| 擅长 | SSL、静态文件、高吞吐 | 服务路由、业务过滤 |



# SpringCloud 幂等性
> **幂等：同一个请求，重复执行 N 次，产生的业务效果和只执行 1 次完全一样，不会产生脏数据、重复数据。**
SpringCloud微服务场景下，网络抖动、重试、超时、消息重复消费，都会带来重复请求问题，所以必须做幂等。

> 数学概念：`f(f(x)) = f(x)`，执行一次与执行多次结果相同。

## 为什么SpringCloud微服务特别需要幂等？
1. **RPC重试**：OpenFeign、RocketMQ/Kafka消息队列、网关，超时会自动重试调用接口。
2. **网络超时**：服务已经执行业务成功，但是响应包网络丢了；客户端认为失败，发起第二次调用。
3. **消息队列重复消费**：MQ至少一次投递（At‑Least‑Once），消息可能重复投递。
4. **前端重复提交**：用户重复点击提交按钮。

> ⚠️重点：**幂等不是让接口不报错；而是重复调用不会改变业务状态，不会生成多条订单、多次扣款。**

## 常见四种实现方案（SpringCloud面试高频）
### 1. 唯一业务ID（业务主键，最常用）
业务生成全局唯一标识：订单号、流水号 `requestId`。
- 逻辑：执行业务前，先判断这个id是否已经处理过；已处理直接返回成功；未处理执行业务。
- 存储：MySQL、Redis记录已处理标识。
- 示例：创建订单用 `orderNo`；同一个orderNo重复过来，直接返回，不要新建订单。

> MySQL实现：唯一索引；或者一张幂等记录表 `idempotent(id,biz_id,status)`。

### 2. 数据库唯一索引（数据库层面天然幂等）
给业务字段加唯一索引。
例：`order_no` 设置唯一索引。
- 重复插入相同order_no，数据库抛出唯一索引冲突异常；业务捕获异常，当成“已经处理成功”返回。
> blocker：只适合**插入场景**；更新场景不适用。

### 3. 状态机控制（订单、流程类业务）
业务有明确状态流转：例如订单：`待支付 → 已支付 → 已取消`
> 更新的时候带上状态条件：
```sql
update t_order set status='PAID' where order_no=xxx and status='WAIT_PAY'
```
只有当前状态是待支付，才允许变更为已支付。重复执行第二次，where条件不命中，更新行数0，业务不做处理。
> 非常适合订单状态流转，SpringCloud订单系统大量使用。

### 4. Token令牌机制（针对前端请求）
1. 客户端请求服务端先获取一个**唯一token**。
2. 提交业务请求的时候带上token。
3. 服务端校验token：校验通过立刻删除token；后续重复携带同一个token，校验失败拒绝请求。
> 适合防止前端重复点击；**不适合MQ消息重复消费场景**。

### 5. Redis 防重（SETNX）
执行业务前，Redis `setnx(bizId,1,expire)`。
- 设置成功：执行业务；
- 设置失败：代表已经处理过，直接返回。
> blocker：要考虑Redis和数据库数据一致性问题；Redis宕机丢失key会导致幂等失效。

## 区分两个极易混淆概念
1. **事务**：保证一组操作要么全部成功，要么全部失败。解决**数据一致性**。
2. **幂等**：解决**重复调用带来的数据错乱**。
> ❗事务不能解决幂等！即使加了事务，重复调用接口依旧会产生脏数据。二者互补，不能互相替代。

## SpringCloud下典型场景举例
1. Feign调用超时重试：A调用B，B已经完成扣款，响应丢在网络；A超时重试，B不能扣第二次钱 → 需要幂等。
2. RocketMQ消息重复消费：同一个订单消息多次投递，不能生成多笔订单 → 需要幂等。

## blocker坑点（面试常问）
1. ❌不要以为MQ开启手动ACK就解决幂等；MQ只是控制确认，消息依旧可能重复投递，消费逻辑仍然要幂等。
2. ❌不要靠判断返回码做幂等；服务执行成功响应丢失，客户端拿到超时，会重试。
3. ❌select查询本身天然幂等；查询接口不用做幂等；**写接口（insert/update）才需要重点考虑幂等**。
4. Redis做幂等要思考：业务执行成功，Redis宕机，key没写入，后续重复请求穿透。

## 面试口述小抄
> 幂等含义：同一个请求重复执行多次，业务结果和执行一次相同。
> SpringCloud微服务下，Feign重试、网络超时、MQ至少一次投递都会产生重复请求。
> 常见实现：业务唯一ID、数据库唯一索引、状态机、Token令牌、Redis SETNX。
> 注意事务不等于幂等，事务解决一致性，幂等解决重复调用问题；查询天然幂等，写接口需要做幂等。
