# 六、Redis 持久化机制（Persistence）详解

Redis 是**内存数据库**，所有数据默认存储在内存中。一旦进程宕机、服务器重启或断电，内存数据会全部丢失。为了保证数据不丢失、支持故障恢复，Redis 提供了两套成熟的持久化方案：**RDB 快照持久化**、**AOF 日志持久化**，同时支持 **RDB\+AOF 混合持久化**模式，兼顾恢复速度与数据安全性。

持久化核心作用：**将内存数据落地到磁盘，重启后通过磁盘文件恢复内存数据**。

## 6\.1 RDB 快照持久化（Redis Database）

### 6\.1\.1 核心原理

RDB 是**全量快照机制**：在指定时机，将 Redis 内存中**当前时刻的所有数据集**以**高度压缩的二进制格式**一次性落地写入磁盘，生成 `dump.rdb` 快照文件。RDB 属于**静态快照备份**，不记录操作过程，只保留最终数据结果。

核心特性：RDB 保存的是**某一个时间点的完整内存镜像**，不保存增量操作日志、不记录命令流水。Redis 宕机重启时，直接加载二进制快照文件，一次性还原全量内存数据，恢复效率极高。同时 Redis 默认优先加载 AOF 文件，仅未开启 AOF 时才会加载 RDB 文件恢复数据。

### 6\.1\.2 底层执行流程（fork 写时复制）

为避免持久化阻塞主线程处理客户端请求，RDB 全程依赖 **fork 子进程 \+ 写时复制（COW）** 机制：

1. **主进程 fork 子进程**：执行 BGSAVE 时，主进程调用 Linux fork\(\) 函数创建子进程。fork 机制仅复制主进程的内存页表、进程上下文，**不拷贝任何实际数据**，瞬间完成、CPU 开销极低。此时父子进程共享同一份内存数据。

2. **子进程遍历内存生成快照**：子进程创建完成后，独立遍历共享内存中的全量数据，将数据以二进制格式写入磁盘**临时文件**，而非直接写入正式的 dump\.rdb，为后续原子替换做铺垫。

3. **写时复制（COW）数据一致性保障（核心原理详解）**：fork子进程的瞬间，子进程不会拷贝主进程的全部内存数据，仅共享主进程的内存页表，此时父子进程共用同一份内存数据，几乎无性能开销。fork完成后，子进程开始静态读取当前时刻的内存数据、生成RDB快照；同时主进程可正常处理客户端的读写请求，不被阻塞。
操作系统会开启写时复制机制：**只有主进程对某一块内存数据执行修改、删除等写操作时，系统才会单独复制一份被修改的内存页**，主进程在新内存页中更新数据，而子进程依旧读取fork瞬间的原始内存数据。
简单来说：**只读不复制、写才复制**，这就保证了子进程生成的RDB快照，是fork那一刻完整、一致的静态全量数据，不会因为主进程后续修改数据出现快照错乱、残缺的问题。

4. **原子替换文件（磁盘容错机制）**：子进程不会直接覆盖正式的 `dump.rdb` 文件，而是先把快照数据写入磁盘临时文件。待文件**完整写入、校验无误**后，再通过操作系统原子机制，用临时文件整体替换正式的`dump.rdb`。该机制保证正式 RDB 文件永远处于“完整可用”状态，避免写入中断、宕机导致文件半截损坏、数据丢失。**注意：该机制是磁盘文件层面的容错，和内存写时复制 COW 无关。**

### 6\.1\.3 触发方式（自动 \+ 手动）

#### 1）自动触发（redis\.conf 配置）

满足任意一条阈值，后台自动执行 BGSAVE：

```Plain Text
# 3600秒(1小时)内有至少1次数据修改，触发快照
save 3600 1
# 300秒(5分钟)内有至少100次数据修改，触发快照
save 300 100
# 60秒(1分钟)内有至少10000次数据修改，触发快照
save 60 10000
```

配置本质是**频率阈值兜底**：低频率大改动、高频率小改动都会触发持久化。

#### 2）手动触发

- `SAVE`：**主线程阻塞**，全程停止处理客户端请求，直到快照写入完成，生产环境**禁止使用**；

- `BGSAVE`：**非阻塞后台执行**，fork 子进程完成快照，不影响主线程，生产推荐。

### 6\.1\.4 优缺点详解

#### ✅ 优点

- **文件体积小**：二进制压缩格式，单文件存储全量数据，适合冷备份、异地容灾；

- **恢复速度极快**：直接加载二进制镜像，无需回放命令，大数据量恢复效率远高于 AOF；

- **性能开销低**：仅 fork 瞬间短暂开销，子进程完成 IO 写入，主线程几乎无压力。

#### ❌ 缺点

- **存在明确的数据丢失风险**：RDB 是间隔性全量快照，两次快照之间的所有增量数据仅驻留内存。若在此期间服务器宕机、进程被杀，**上一次快照之后的所有新增/修改数据会全部丢失**，无法满足高可靠业务场景。

- **不适合高频实时持久化**：频繁快照会加重磁盘 IO 与 fork 开销。

## 6\.2 AOF 追加日志持久化（Append Only File）

### 6\.2\.1 核心原理

AOF 是**增量日志机制**：不保存内存数据快照，全程记录客户端所有**写操作命令**（增、删、改，查询命令不记录），并以标准 Redis 协议文本格式，持续追加到 `appendonly.aof` 日志文件末尾，属于「操作流水日志」。

Redis 故障重启恢复时，会读取完整 AOF 日志，**从第一条命令开始逐条回放执行**，重新构建完整内存数据集。AOF 默认关闭，需要手动开启；相较于 RDB，AOF 极大降低了数据丢失概率，是 Redis 保障数据安全的核心机制。

### 6\.2\.2 核心配置与刷盘策略

```Plain Text
# 开启AOF持久化（默认no关闭）
appendonly yes

# 三种磁盘刷盘策略（核心取舍：数据安全 vs 性能）
appendfsync always    # 每条写命令执行完立刻刷盘，0数据丢失，性能最差
appendfsync everysec  # 每秒批量刷盘，最多丢失1秒数据，性能均衡（生产默认推荐）
appendfsync no        # 交给操作系统自动刷盘，性能最高，丢失数据不可控
```

### 6\.2\.3 AOF 重写机制（核心优化、解决日志无限膨胀）

AOF 采用纯追加写入模式，**如果没有重写机制，Redis 长期不重启、持续接收写请求，AOF 文件会无限膨胀变大**。因为 AOF 只会无脑追加命令，不会自动清理历史冗余内容：同一个key反复修改、反复自增、过期删除的key，都会累积大量重复、无效命令，最终导致文件臃肿、磁盘占满、重启恢复速度极慢。

为此 Redis 专门设计 **AOF 重写（Rewrite）** 核心优化机制：不基于旧日志精简，而是直接读取**当前内存最新的真实数据**，反向生成最简、无冗余的命令日志，替换旧的大体积 AOF 文件，从根本上解决长期运行日志无限膨胀的问题。

#### 重写核心逻辑

- 多条重复增量命令 → 合并为一条最终结果命令（如千次 INCR 合并为一条 SET）；

- 过期、删除、无效命令直接清理剔除；

- 重写全程后台子进程完成，不阻塞主线程，不影响业务运行。

#### 触发方式

- **自动重写（默认开启，解决长期运行膨胀问题）**：Redis 内置阈值配置，当 AOF 文件体积增长到指定倍数、达到指定大小，会**后台自动触发重写**，无需人工干预，长期不重启也不会无限涨文件；

- 手动重写：执行 `BGREWRITEAOF` 命令，后台非阻塞重写，随时手动精简日志。

#### 重写期间数据一致性保障

AOF 重写全程由子进程后台执行，不阻塞主线程处理业务。为保证重写期间数据不丢失、数据一致，重写过程中客户端新增的写命令，会**同时追加到旧 AOF 文件与重写专属缓冲区**。旧 AOF 持续对外服务、保证数据落盘；重写完成后，缓冲区的增量命令会合并到新 AOF 文件，最后原子替换旧文件，全程零数据丢失、零业务中断。

### 6\.2\.4 优缺点详解

#### ✅ 优点

- **数据安全性极高**：默认 everysec 策略最多丢失 1 秒数据，always 策略可做到零丢失；

- **日志可读可修复**：文本协议格式，可手动打开删除误操作命令，修复异常数据；

- **增量写入开销小**：正常运行仅追加日志，无需全量遍历内存。

#### ❌ 缺点

- **文件体积远大于 RDB**：文本日志冗余度高，同等数据量下文件更大；

- **数据恢复速度慢**：重启恢复需要逐条解析、校验、执行日志命令，而非直接加载镜像。数据量越大，回放耗时越长，恢复速度远低于二进制的 RDB 快照。

- **高频刷盘有性能损耗**：always 策略严重降低 Redis 吞吐量。

## 6\.3 RDB \+ AOF 混合持久化（生产推荐最优方案）

### 6\.3\.1 核心痛点

- 纯 RDB：恢复快，但会丢失快照间隔内数据，安全性差；

- 纯 AOF：数据安全，但文件大、恢复慢、长期运行日志冗余。

### 6\.3\.2 混合模式原理（Redis 4\.0\+ 新增）

Redis 4\.0 及以上推出 RDB\+AOF 混合持久化，彻底解决纯 RDB 和纯 AOF 的固有缺陷。开启混合持久化后，**AOF 重写逻辑会彻底变更**，不再生成纯文本命令日志，而是采用「全量快照\+增量日志」的组合形式生成新 AOF 文件：

1. 先将**当前全量内存数据以 RDB 二进制快照**写入 AOF 文件头部；

2. 再追加**重写时刻之后的增量 AOF 命令日志**；

最终生成的混合 AOF 文件结构清晰、优势互补：**文件头部为 RDB 二进制全量快照、文件尾部为重写完成后的增量 AOF 命令日志**。既保留了 RDB 的快速恢复能力，又保留了 AOF 的高数据安全性。

**三种持久化模式核心逻辑终极总结**：
1\. **纯RDB**：仅保存某一时刻的全量内存快照，只留存结果、不记录过程，恢复速度快，但会丢失两次快照之间的增量数据。
2\. **纯AOF**：全程记录从服务启动后所有的写命令流水，重启逐条回放恢复数据，数据安全性高，依靠自动重写机制防止日志无限膨胀，但长期运行仍存在一定冗余命令，文件偏大、恢复慢。
3\. **RDB\+AOF混合持久化**：依托AOF重写机制实现极致去重优化，文件由「全量RDB快照 \+ 快照之后的增量AOF日志」组成，尾部AOF命令均为快照未包含的全新数据，无冗余重复，彻底解决长期运行文件膨胀问题，同时兼顾RDB的恢复速度和AOF的数据安全性。**核心关键**：未开启混合模式时，AOF日志包含大量与RDB快照重复的命令；仅开启混合持久化并完成重写后，才能实现「快照存历史、AOF存增量」的纯净结构。

### 6\.3\.3 核心配置

```Plain Text
# 开启RDB+AOF混合持久化（默认开启）
aof-use-rdb-preamble yes
```

### 6\.3\.4 核心优势

- **兼顾极速恢复 \+ 高数据安全**：重启优先加载头部 RDB 快照快速恢复全量数据，再回放尾部少量增量日志，恢复速度接近纯 RDB，数据安全接近纯 AOF；

- **大幅压缩 AOF 文件体积**：替代海量冗余命令，文件更小、更整洁，完美适配 Redis 长期不重启的运行场景；

- **规避双模式加载冲突**：Redis 重启默认优先加载 AOF 文件，混合模式统一整合全量\+增量数据，无需手动抉择加载 RDB 还是 AOF，避免双持久化模式带来的数据覆盖、加载错乱问题。

## 6\.4 三种持久化方案横向对比（面试必背）

|特性|纯 RDB|纯 AOF|RDB\+AOF 混合|
|---|---|---|---|
|数据安全性|低（分钟级丢失）|高（秒级/零丢失）|极高|
|文件体积|最小（二进制压缩）|最大（文本日志）|中等且可控（自动重写压缩）|
|恢复速度|极快|慢（逐条回放）|快（接近RDB）|
|性能开销|低|中（取决于刷盘策略）|均衡最优|
|适用场景|冷备份、可容忍少量数据丢失|数据零容忍丢失、金融核心业务|**绝大多数生产环境首选、支持长期不重启稳定运行**|

## 6\.5 生产最佳实践总结

1. **禁止单独使用纯 RDB**：存在数据丢失风险，无法满足线上数据可靠性要求；

2. **不推荐单独使用纯 AOF**：文件臃肿、恢复慢，长期运行维护成本高；

3. **线上统一开启混合持久化**：`appendonly yes + aof-use-rdb-preamble yes`，兼顾性能、恢复速度、数据安全；

4. 刷盘策略固定使用 **appendfsync everysec**，平衡性能与数据安全；

5. 定时备份 RDB/AOF 文件，用于异地容灾、故障回滚；

6. 依赖AOF自动重写机制，保障Redis**长期不重启、7\*24运行**场景下，AOF文件不会无限膨胀，稳定可控。
