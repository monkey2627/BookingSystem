## 三、分场景详情

### 3.1 冒烟测试

2 VU 运行约 1 分钟，串行执行"商家搜索 → 商家详情"链路。

- p(95) = **40.6ms**，远低于 500ms 阈值
- 最大响应时间 521ms（单次偶发，非系统性问题）
- 全程 0 错误，接口链路完全可用

### 3.2 基准负载测试（50 VU × 10min）

模拟 50 个并发用户稳定访问商家搜索和商家详情接口。

- 稳态 RPS **50.7**，Iterations **22,200**
- p(95) = **10.2ms**，p(90) = **7.6ms**
- 全程 0 HTTP 错误，0 业务断言失败
- 最大响应时间 220ms，属于偶发长尾，无系统性抖动

**结论：** 50 VU 下系统表现稳定，响应时间极低，具备充分的扩容余量。

### 3.3 压力测试（0→200 VU）

从 0 渐增至 200 VU，持续冲击商家详情接口（含 Redis Cache Aside 缓存）。

- RPS 峰值 **192.6**，总请求 153,477
- p(95) = **8.87ms**，**低于基准负载的 10.2ms**
- 全程 0 错误，所有 306,732 个断言全部通过
- 最大响应时间 105.7ms，无崩溃点出现

> **为何压力测试 RT 反而低于基准？**  
> stress 场景集中打商家详情接口（`GET /api/merchant/{id}`），该接口采用 Redis Cache Aside + Redisson 防击穿双重保护。随并发增大，缓存命中率持续提升，绝大多数请求直接命中 Redis，无需访问 MySQL，RT 因此更低。这是 Redis 缓存在高并发下的正常表现，不代表系统在 200 VU 下无压力，而是测试场景命中了缓存热点。

**结论：** 200 VU 下商家详情接口凭借 Redis 缓存实现了极低 RT，未发现系统崩溃点。如需寻找真正的容量上限，需针对写路径（预约创建、状态流转等）设计独立压力场景。

### 3.4 尖峰测试（100 VU 抢档期）

**本次结果无效。**

`setup_data.rushScheduleId = null`，说明 setup 阶段未能找到可抢的档期。实际产生的 106 次请求来自 setup 阶段的登录和商家搜索，核心的 `POST /api/schedule/{id}/rush` 请求量为 0。

**根因：** 播种脚本（03_seed_schedules.js）将抢档期的 `rushOpenTime` 设为档期当天的 `10:00:00`（未来时间），而测试运行时尚未到达该时间，后端返回 `SCHEDULE_NOT_OPEN(10002)`。spike 的 setup 函数仅查找 `rushOpenTime` 已过的档期，因此返回 null，100 个 VU 全部在函数入口处 `return`，跳过了实际请求。

**已修复（2026-09-04）：**
1. `03_seed_schedules.js`：抢档期的 `rushOpenTime` 改为当前时间往前推 1 小时，保证播种后立即可抢
2. `04_spike_rush.js`：setup 查找条件从 `status=0` 改为 `rushOpenTime <= now`，精确匹配已开放档期

修复后需重新播种并执行 spike 测试。

本次未执行（耗时约 1 小时，不在当次测试计划内）。建议在功能稳定后单独安排，重点观察：

## 五、结论与建议

### 结论

| 维度 | 状态 | 说明 |
|------|------|------|
| 接口可用性 | ✅ 正常 | 三个有效场景均 0 错误 |
| 读接口性能 | ✅ 优秀 | 200 VU 下 p95 仅 8.87ms，Redis 缓存效果显著 |
| 系统稳定性 | ✅ 稳定 | 压力测试未发现崩溃点或错误率上升 |
| 抢档期原子性 | ⚠️ 待验证 | 数据问题导致本次无效，修复后需重测 |
| 写路径性能 | ⚠️ 未覆盖 | 预约创建、状态流转等写接口未纳入本次测试 |

### 后续建议

1. **重跑 spike 测试：** 脚本已修复，重新播种后执行，验证 Lua 脚本的原子性（最终队列人数应 ≤ 5）
2. **补充写路径压测：** 针对 `POST /api/booking`（预约创建）设计独立负载场景，该接口涉及 Redisson 分布式锁 + 数据库写入，是实际系统瓶颈更可能出现的地方
3. **安排浸泡测试：** 30 VU × 1h，配合 JVM 监控，排查潜在内存泄漏
4. **ES 搜索性能：** 本次未单独测试 `/api/merchant/search`（ES multi_match），建议在商家数量扩大后补测，验证 ES 分页和 IK 分词性能
